# Masarat

## What this is

Masarat is an electronic transport, manifests, and tax-collection system tailored for Sudan. Its goal is to improve how transport taxes are paid and collected.

It started as an **Electron MVP / demo** for the relevant government agency (kept, frozen, in `apps/desktop-demo`). We are now building the **production web version**. External integrations (E-Sali, banks) are still **simulated** behind interfaces. OCR was removed (see *Planned: document review*).

## App shape

Three web apps and one API, each on its own (sub)domain:

1. **Site** (`apps/site`, `masarat.com`): the public landing page, **login for everyone**, company sign-up, the forced password change, and the public **verify page** a manifest's QR code opens. A signed-in user is sent to their portal (except from the verify page).
2. **Company portal** (`apps/owner-portal`, `owner.masarat.com`; the folder and subdomain keep their old names for now): used by **transport companies** (شركات النقل) and their staff. It has the trips, vehicles, drivers, profile and, by permission, *Team*, *Branches* and *Roles*.
3. **Government portal** (`apps/govt-portal`, `govt.masarat.com`): used by government staff. It has the dashboard, search, exports and, for government admins, *Taxes and fees* and *Users*.
4. **API** (`apps/api`, `api.masarat.com`): one Hono app on Bun that all three call.

The Electron demo showed both panels in one window with a toggle. The web apps don't: the account's kind (`users.kind`: `company` or `govt`) decides the portal.

**Terms**: a *transport company* (code: `company`; "fleet owner" in the MVP) signs up, owns vehicles and drivers, and books trips at its *branches*. Its people are *members*, each with a *role*. The government's people are *users* of the government portal, with a government role.

## Login and sessions

- **One login, on masarat.com** (`apps/site`): username and password only; the account's kind picks the portal. After login the site goes to `?next=` when it's a page of the user's own portal (`destinationFor` in `packages/ui/src/lib/urls.ts`; anything else would be an open redirect), otherwise to the portal's home. A signed-in user who opens masarat.com is sent straight on.
- **The portals have no login page.** `AppShell` asks `GET /auth/me`; without a session it sends the browser to `masarat.com/login?next=<this page>`, a user of the other kind to their own portal, and a user with a temporary password to `masarat.com/change-password`. Any API call that answers 401 fires `SIGNED_OUT_EVENT` (`@masarat/api-client`), which does the same. Logout returns to masarat.com.
- **Sessions** (`services/sessions.ts`, `sessions` table): a random 32-byte token in the `masarat_session` cookie (HttpOnly, SameSite=Lax, Secure over HTTPS, `Domain=COOKIE_DOMAIN` = `.masarat.com` in production so every subdomain sends it; unset locally, where one host-only cookie on `localhost` covers every port). Only the token's SHA-256 is stored. A session ends after **2 h idle** or **12 h** in all, and at once when the account is disabled or its password reset. Changing your own password signs out your other sessions. Expired rows are purged on startup and hourly.
- **Passwords**: Argon2id (`Bun.password`). Older scrypt hashes still verify and are rehashed at the next login.
- **Rate limit** (`login_attempts`): 5 failures per username or 20 per IP in 15 minutes give `too_many_attempts`. A wrong password and an unknown username answer the same (`invalid_credentials`, timed alike); `account_disabled` is only told after the password checks out.
- **CSRF and CORS** (`src/http/middleware.ts`, `src/app.ts`): requests that change something must carry an `Origin` that is one of `SITE_URL`, `OWNER_URL`, `GOVT_URL`; CORS allows exactly those, with credentials.
- **Sign-up creates a transport company** (`signUp` in `services/auth.ts`, `createCompany` in `services/companies.ts`): the company (name required, address and TIN optional), its three built-in roles, and the person signing up as its **company admin**. Government accounts are never self-made.
- **Accounts are managed by admins** (`services/members.ts`, one set of rules for both sides; UI `packages/ui/src/components/members/TeamPanel.tsx`): a company admin in Company portal → *Team* (`/members`), a government admin in Government portal → *Users* (`/govt/users`). Create (a 12-character temporary password shown once, a role and, for a branch role, the branch), disable / enable, reset password, change role / branch. An admin can't change their own account there, and each side always keeps one active admin (`last_admin`; the admins' rows are locked, so two admins demoting each other at once can't both succeed). Accounts with a temporary password (`must_change_password`) can only call `/auth/me`, `/auth/change-password` and `/auth/logout` until they pick their own. One person belongs to one company.
- **The first government admin** of a new deployment comes from the server: `bun run --filter @masarat/api user:create-admin <username> <phone> "<full name>"` prints its temporary password.
- **Roles and permissions** (`packages/shared/src/permissions.ts`): the typed lists `COMPANY_PERMISSIONS` (`trips.view`, `trips.edit`, `trips.bill`, `templates.use`, `templates.manage`, `fleet.view` / `.manage`, `drivers.view` / `.manage`, `company.profile`, `branches.manage`, `members.manage`, `roles.manage`) and `GOVT_PERMISSIONS` (`govt.dashboard`, `govt.search`, `govt.exports`, `govt.charges`, `govt.settings`, `govt.users`) are the single source: the `role_permissions` CHECK is built from them (a test checks it), routes declare what they need with `requirePermission(...)` (any of), and the portals ask `useCan()(…)` (`packages/ui/src/lib/account.tsx`) to show only what the user can use. Doing implies seeing (`withImplied`: `fleet.manage` adds `fleet.view`, …).
  - A role (`roles`) has a name, a **scope** (`branch`: the member works at one branch, `users.branch_id`, and sees and books only its trips; `company`: every branch) and its permissions (`role_permissions`). Built-in roles have a `key`.
  - Every company starts with **company admin** (locked, every company permission, from the code), **clerk** (branch: view, book and bill trips, and book from templates) and **accountant** (company-wide: view and bill trips, view vehicles and drivers). The clerk and accountant can be edited; a company adds its own roles with checkboxes in *Roles* (`services/roles.ts`; a role in use can't be deleted or change scope).
  - The government has two **fixed** roles (no `company_id`): **government admin** (everything, including *Taxes and fees*, *Settings* and *Users*) and **government agent** (dashboard, search, exports). A reviewer role is planned (see *Planned: document review*).
  - Each request loads the account with its company, role, branch and permissions (`accountOf` in `services/access.ts`), so a role change takes effect on the next request. `/auth/me` returns it (`AuthUser`).
  - **Scope in the queries**: the company services take a `CompanyScope` (`{ companyId, branchId | null }`, from `scopeOf`), the government's read-only views `null`; `tripScopeCondition` adds `manifests.company_id` (the vehicle's company, kept on the trip so company lists read one index, `(company_id, departure_at)`) and, for a branch member, `manifests.branch_id` (`(branch_id, departure_at)`) to every trip query, so another company's or branch's trip answers 404. Every new trip sets `company_id` (`createTrip`, the demo and load-test seeders).
- **Phone numbers** (`packages/shared/src/phone.ts`): every account (company members, government users) and every driver has a **Sudanese mobile number**, for SMS later (one-time codes, notifications). `normalizeSudanPhone` accepts `0912345678`, `912345678`, `+249…`, `00249…` or `249…` with spaces or dashes, takes mobile numbers starting with 9 or 1, and stores `+249912345678`; `formatSudanPhone` shows `+249 91 234 5678`. An account's number is unique across all accounts (`users_phone_unique`, `phone_taken`); a driver's is unique among the company's drivers. Senders' and receivers' phones may be foreign (`normalizePhone` in `fleet.ts`).
- **Language**: every site opens in **Arabic** unless the user picked English. The choice is the `masarat_lang` cookie (a year, on `VITE_COOKIE_DOMAIN` = `.masarat.com` in production, so the three sites share it; host-only `localhost` locally), set in `packages/ui/src/i18n/index.ts`. Missing keys fall back to English.
- **Demo mode** (`DEMO_MODE=true`, never in production): seeds the demo data, shows the demo accounts on the login page (`GET /config`), and allows the demo-only actions (simulated payment, regenerate demo data).

## Production status

Login, both portals and the verify page work end to end on Postgres.

- **Both portals are wired** to the API (`apps/api/src/routes/`, listed in `apps/api/ROUTES.md`): the company's `/vehicles`, `/drivers`, `/trips`, `/documents`, `/company`, `/branches`, `/roles`, `/members`, and the government's `/govt/*`. Each route takes the account from the session (`c.get('user')`, an `AuthUser`), checks its permission, and passes its company scope to the service (`null` for the government's read-only views of any company).
- `@masarat/api-client` follows the old `window.api`, except where the desktop did things natively: files are uploaded (`documents.upload`) and fetched as blobs (`documents.file`, `govt.documentFile`), exports come back as a file to save (`lib/saveFile.ts`), and documents and the report print from the browser. CORS exposes `Content-Disposition` and `X-Export-Rows`, so the client can read a download's name and an export's row counts.
- **Deployment notes so far**: trip attachments live on the API server's disk (`STORAGE_DIR`), so there is one API server, with that folder on a persistent, backed-up volume. The API runs on Sudan time (`TZ=Africa/Khartoum`, see Tech stack).
- The database is **Postgres**. File storage and deployment are still open questions for the production brainstorm.
- **The data model is being revised.** The rules below describe the behaviour carried over from the MVP.
- IPC channel names in the rules below (`documents:pick`, `govt:get-trip`, …) are the demo's, and each one becomes an API route. Anything the desktop did with native dialogs or `printToPDF` (picking files, opening files, saving PDFs, export save dialogs) still has to be redone for the browser. On the API side that's already started: uploads go through `stageDocument`, and `exportData` returns the files.

## Core flow (transport company)

1. **Log in.**
2. **Create a new trip** with its details: the vehicle, the route, the departure and estimated arrival, and what it carries: **cargo** (a truck or tanker) or **passengers** (a bus).
3. **Tax calculation**: the system computes the tax due for the trip.
4. **Bill generation**: the app simulates an **E-Sali (Esali) API** call that returns a **bill ID**.
5. **Payment**: the user pays that bill ID through **Bankak** or another bank. The MVP simulates this.
6. **Payment confirmation**: once the system confirms payment, it moves on to the next step.
7. **Documents**: the app issues the **electronic payment receipt** and the **authorized manifest** (تصريح الحركة), each with a barcode of its number and a **QR code** that traffic/checkpoint **officers can scan to verify it quickly**.

## Fleet & trips rules

- **Plate numbers** (`packages/shared/src/plate.ts`): a state code of 1-2 letters (KH, RS, NK, …), a series from 1 to 99, then a number from 1 to 99999. They are stored in English as `"KH 12/34567"` and shown in Arabic as `"خ ١٢ / ٣٤٥٦٧"` (letters → series → number, read right to left), with Eastern Arabic digits. Validation happens in the UI and services, not as a DB constraint.
- **Digits**: plates are the only thing shown with Eastern Arabic digits (badge, plate text, plate inputs). Every other number, amount and date uses English digits, even in the Arabic UI. Stored and backend values are always English.
- **Pricing is a development formula** (`services/pricing.ts`, the `PricingService` interface): how cargo and tickets are really priced isn't known yet. `FormulaPricing` uses `pricing_rates`: a rate per km for each cargo type, and **80 SDG per km per seat** for a passenger ticket (`calculateTicketPrice`; Khartoum → Port Sudan ≈ 875 km ≈ 70,000 SDG). **`APP_ENV`** (`development` | `production`, in `config.ts`): with `APP_ENV=production` the API refuses to start while trips are priced by the formula (`assertPricingAllowed` in `index.ts`), so a real `PricingService` has to replace it first. Trip saving and billing price through `pricing`, never the tables directly.
- **Trip cost** (`calculateItemsCost` in `packages/shared/src/tax.ts`): the sum of the cargo items' costs. Each item costs `rate_per_km × distance_km × quantity / per_quantity` at its own cargo type's rate (`pricing_rates`), with its quantity in the rate's unit. Items keep a snapshot of the rate and their cost. Distance is the haversine distance between the cities × a 1.3 road factor (an estimate until real routing exists).
- **Taxes and fees ("charges")** (`charges` table, `calculateCharges` in `packages/shared/src/tax.ts`): one list, each charge a **percentage** of the trip cost (`kind = 'percent'`, in basis points, 1700 = 17%) or a **fixed amount** in whole SDG (`'fixed'`, not taxed).
  - Each charge has its own value for **cargo trips** and for **passenger trips** (`cargo_value`, `passenger_value`); null means it isn't charged on that kind of trip. It can be switched off (`active`).
  - Four are built in (`BUILTIN_CHARGE_CODES`, `builtin`): VAT (17%), business profit tax (3%), locality tax (2%) and the **manifest fee** (رسوم المنفيست, 1500 SDG), with the same values for both kinds. They can be renamed, changed and switched off, not removed. The admin adds **custom** ones (code `custom_<id>`).
  - Names are stored in both languages (`name`, `name_ar`), not in the translations; `format.chargeName` / `format.taxLine` pick the current language.
  - A bill's lines are the active charges with a value for its kind: the percentages first, then the fixed fees, each in list order (`sort`) and rounded to whole SDG; the total is their sum.
  - The **bill is the total of the taxes and fees** (`manifests.tax_amount`). The trip cost is shown for reference.
  - A trip's lines are kept in `manifest_charges` with the charge's code, **name and value at the time** (a fixed fee has `rate_bps = null`). Drafts are priced when saved, and *Generate bill ID* reprices them at the current charges; from then on they're frozen, so renaming or changing a charge never changes a bill already issued.
  - A trip's kind (`manifests.category`: `cargo` or `passenger`) comes from its vehicle (`tripCategoryFor`: a bus carries passengers), and picks the charges' value.
  - The API recomputes cost and charges on save; the portal's preview is never trusted.
- **Settings** (Government portal → *Settings*, `services/settings.ts`, `GET|PUT /govt/settings`, `govt.settings`: government admins only; `system_settings`, one row per key): per kind of trip, how long documents stay **valid after the estimated arrival** (0–720 h, default 24) and the **average speed** the trip form suggests the arrival from (10–150 km/h, defaults 50 for cargo and 70 for passengers). A new margin applies to documents issued afterwards.
- **Taxes and fees screen** (Government portal → *Taxes and fees*, `services/charges.ts`, `GET|POST /govt/charges`, `PUT /govt/charges/:id`, `govt.charges`: government admins only): a table of the charges with their cargo and passenger values; *Add a tax or fee* and the edit dialog set both names, the kind (fixed once created), each kind of trip's value or "not charged", and on / off. Percentages from 0 to 100% with up to 2 decimals, fees from 0 to 1,000,000 SDG; a charge needs a value for at least one kind (`invalid_charge`). Each changed field is logged in `charge_changes` (who, which field, old and new value as text). Approval comes later.
- **Profile** (*Profile* section): every member edits their own name and phone (`PATCH /auth/profile`, `updateProfile`). Below it, the **company's details** (`PUT /company`, `updateCompany` in `services/companies.ts`, `company.profile`; read-only for others): name, address and TIN (الرقم الضريبي), the **carrier details** printed on its manifests. Sign-up also asks for the address and TIN (optional there). Limits: address up to 200 characters, TIN up to 30.
- **Branches** (*Branches* section, `services/branches.ts`, `branches.manage`; every member can list them): where the company books trips, often a booth at a land port: a name (unique in the company) and a city. A closed branch keeps its trips and members but takes no new trips (`branch_inactive`).
- **Every trip is booked at a branch** (`manifests.branch_id`, and `created_by` the member who booked it). A branch member's trips are always their own branch's, whatever the form sends; a company-wide member picks the branch in the trip form (`branch_required`). Trips can be filtered and grouped by branch.
- **Vehicles and drivers belong to the company**, not to a branch (`company_id`). Seeing them needs `fleet.view` / `drivers.view` or `trips.view` (the trip form lists them); changing them `fleet.manage` / `drivers.manage`.
- **Vehicles** need a **registration number** (رقم الترخيص, `vehicles.registration_no`, up to 30 characters) when added or edited. It is null only for vehicles added before it existed; the vehicles list flags those.
- **Drivers** (*Drivers* section, `services/drivers.ts`, `drivers` table): each company keeps a list of drivers with a name and phone. Phones are Sudanese mobile numbers (see *Phone numbers*) and are unique per company.
- **Manifest details** (what the authorized manifest prints): each trip has a **trip type** (`domestic` / `import` / `export`), up to 3 **trailer plates** (`manifest_trailers`, each different from the vehicle's plate), a **driver** from the company's list, and a **sender** and **receiver** (name, address, phone). Each cargo item also has a **packing type** (free text; common types in `PACKING_SUGGESTIONS` and the company's earlier ones are suggested), a **number of packages** and optional **notes**. Its quantity is shown as the **weight**.
  - Drafts can leave the driver, sender, receiver and packing details empty, but what is entered is validated.
  - *Generate bill ID* needs `missingForBilling` (`packages/shared/src/fleet.ts`) to be empty: the driver, a complete sender and receiver, the packing type and package count on every item, and the company's address and TIN. Otherwise it returns `incomplete_manifest`, and the trip page lists what's missing.
  - The manifest keeps its own copy of the driver's name and phone (saved with the draft and refreshed when the bill is generated) and of the **carrier details** (the company's name, address and TIN, copied when the bill is generated).
  - A driver on a draft can't be deleted (`driver_in_use`); deleting one used only by billed trips sets their `driver_id` to null.
  - `trips:suggestions` returns the senders, receivers and packing types of the trips booked in the last 30 days (`SUGGESTION_DAYS`) for the form.
- **Supporting documents** (`services/documents.ts`, `trip_documents`, UI in the company portal's `trips/DocumentsField.tsx`): a trip can have one file per document type. The commercial invoice and packing list always apply, the certificate of origin for imports, and the import/export authorization for imports and exports (`documentTypesFor`). Files are PDF, JPG or PNG, up to 20 MB, and are optional.
  - *Attach* opens the browser's file picker and uploads the file (`POST /documents`, multipart, its own 20 MB body limit; `documents:pick` in the demo). `stageDocument` checks the extension, size and first bytes (a renamed file of another kind is refused), and writes it to `<STORAGE_DIR>/documents/staging/` (`userData` in the demo), named by a random token kept in memory **with the uploader's id**: nobody else can attach it. Saving the trip moves it to `documents/<manifest id>/` and adds the row. Staging is emptied on startup.
  - Drafts can add, replace or remove attachments; documents of a type the trip no longer needs (after its type changed) are dropped on save. Deleting a draft, or regenerating demo data, removes the folder.
  - *View* opens an attachment in an **in-page preview** (`trips/DocumentPreview.tsx`, both portals): PDFs in the browser's own viewer, images as they are, with *Download* and previous / next (and the arrow keys, following the reading direction) through the trip's documents. The file comes as a blob from `GET /documents/:id/file` (`findOwnedDocumentFile`, sent inline with `nosniff` and `no-store`), so the API never has to allow being framed. In the demo, `documents:open` opened the system viewer.
- **Passenger trips (buses)** (`packages/shared/src/passengers.ts`, `trip_passengers`, UI `trips/PassengersEditor.tsx`): a `bus` is counted in **seats** (`capacity_unit = 'seat'`, whole numbers; only a bus is). Its trips are always **domestic** (they change buses at the border), have no trailers, sender, receiver or documents, and carry **passengers** instead of cargo items.
  - Each passenger: name, ID (**national ID**, 11 digits, or **passport**, 6–20 letters and digits; stored normalized, `normalizeIdNumber`), **seat** (1 to the bus's seats, one passenger per seat) and notes (nationality, …). An **infant** on a passenger's lap shares their seat, has no ticket, may have no ID and is noted رضيع (`checkPassengers`, `seat_taken`, `invalid_passengers`).
  - **Ticket price** = the ticket rate per km per seat × distance (`pricing.ticketPrice`; 80 SDG/km in development); the **trip cost** = ticket price × tickets (everyone with a seat). `cargo_quantity` holds the tickets (unit `seat`), `cargo_type` is null, `ticket_price` the price. Billing reprices the ticket and the charges, then everything is frozen: **no late boarding** (`not_draft`).
  - A draft may have no passengers yet; *Generate bill ID* needs at least one ticket and an ID for everyone with a seat (`passengers`, `passenger_ids` in `missingForBilling`).
  - The company's trips search finds a passenger by name or exact ID number.
- **Departure and arrival** (every trip): `manifests.departure_at` and `arrival_at` (the estimate), entered as local date and time (`YYYY-MM-DDTHH:MM`, `parseLocalDateTime`). The form suggests the arrival as departure + distance ÷ the government's average speed for the kind of trip, rounded up to the quarter hour (`suggestedArrival`), until the member types their own; it must be after the departure (`invalid_arrival`). Filters, sorting and month groups use the departure.
- **Trip templates** (`services/templates.ts`, `/templates`, *Templates* section with `templates.manage`; listed with `templates.use`, a branch member sees their branch's): a passenger trip a company repeats: name, branch, route, a bus, its usual driver, the time of day it leaves and how long it takes. *From a template* in Trips opens the form with them filled in, leaving today (or tomorrow once the time has passed) and arriving after the duration.
- **List tools** (`ui/ListToolbar.tsx`): the company's Trips, Vehicles and Drivers lists have a search box, filters, sort with a direction toggle and, except drivers, group-by with a header row per group (trips show count and total due). The settings are kept per list in `sessionStorage`.
  - **Vehicles and drivers** load in full and filter in the browser (`lib/useListView.ts`).
  - **Trips are paged by the API** (`lib/useServerList.ts`, `GET /trips`, `services/tripList.ts`): numbered pages (`ui/Pagination.tsx`, 25 / 50 / 100 per page), the search debounced. The API searches (`#id`, plate in either script, cities, driver, sender, receiver, item names), filters and sorts. **Grouping works across pages**: rows are ordered by their group first, each page shows the headers of its groups, and each header's count and total due cover the whole group (`groups` in the page). The portal labels the groups from their keys (status, `YYYY-MM`, vehicle id, driver id, `origin-destination` ids, trip kind, cargo type, branch id). The filters' vehicle, driver and branch options come from the company's lists; only company-wide members see the branch filter and group.
- New trips are saved as `draft` manifests. Until their bill ID is generated, drafts can be edited in the same form (*Edit trip*, `updateTrip`) or **deleted** for good, with their items and tax lines (`deleteTrip`). Otherwise both return `not_draft`.

## Billing & certificates rules

- **Flow** (`apps/api/src/services/billing.ts`, UI in `components/trips/TripDetails.tsx`): `draft` → *Generate bill ID* → `billed` (shown as "Pending payment") → the user pays the bill ID from any banking app → *Refresh status* → once E-Sali reports it paid, the payment is recorded, the receipt and the authorized manifest are issued (one `certificates` row) and the manifest becomes `certified` (shown as "Authorized"). Our `payments` row only changes on refresh.
- **E-Sali bill ID** (`packages/shared/src/billing.ts`): `yyyy` `mm` `0dd` (day as 3 digits) + 13 random digits = 22 digits, e.g. `2026110170000123456789`. One bill per manifest; generating again returns the existing bill.
- **E-Sali is simulated** behind the `EsaliGateway` interface in `apps/api/src/services/esali.ts`. The mock keeps E-Sali's side in the `esali_sim_bills` table (simulation only; drop it with the real API). The hidden "⋯ → Pay <billId>" menu on a pending trip marks the bill paid at E-Sali.
- **Documents** (`certificates` table, `components/trips/CertificateModal.tsx`): issued together once the bill is paid, **valid until the estimated arrival plus the government's margin** for the kind of trip (`validUntilFor`, *Settings*, 24 h by default). Always rendered in Arabic (`i18n.getFixedT('ar')` + `createFormatters`), issued by ديوان الضرائب with the Sudan emblem (`assets/sudan-emblem.svg`, Wikimedia Commons). *Print or save as PDF* opens the browser's print dialog (`lib/printDocument.ts`; the page title is set to the receipt number meanwhile, so *Save as PDF* suggests it as the file name). The demo used `webContents.printToPDF`. The `@media print` rules in `main.css` (with `@page` A4, 10 mm) print only the dialog's sheets.
  - **Every page is a fixed A4 sheet** (`DocumentSheet` in `documentParts.tsx`, 190 × 276 mm inside the 10 mm page margin; `.print-sheet ~ .print-sheet` breaks the page). Each sheet repeats the letterhead (authority lines, emblem centred, and on the left the **Code 128 barcode** of the document number with the issue date) and a footer with the **QR at the bottom left** and "صفحة n من N". The barcode carries the MSR-/MNF- number itself, so there is no Arabic caption under it. `documentFrame.ts` builds what a document's sheets repeat.
  - **Page 1** (`ReceiptPage.tsx`) is the **electronic payment receipt** (إيصال سداد إلكتروني), number `MSR-<yyyy>-<manifestId 6 digits>` (`certificate_no`), with the trip cost and each tax and fee line. It fits one page.
  - Then the **authorized manifest** (`ManifestPage.tsx`) (تصريح حركة بضائع بري), number `MNF-<yyyy>-<manifestId 6 digits>` (`manifest_no`). It lists the vehicle, trailers, registration no., route and trip type; a table of the carrier, driver, sender and receiver; the cargo (description, packing, packages, weight, notes); the financial and customs section (قيمة الترحيل = the trip cost, رقم الإقرار الجمركي left blank); and name / signature / date / stamp blocks for the carrier, the driver (received the goods) and the receiver (on delivery). Customs, Zakat and others stamp the printed copy; that's out of scope. A typical trip fits one A4 page.
  - A passenger trip's manifest is the **passenger manifest** (`PassengerManifestPage.tsx`) (كشف ركاب), numbered `PSG-<yyyy>-<manifestId 6 digits>` (`manifestNoFor`), so an officer tells it from the number: the bus, route, departure and arrival, carrier and driver, then the passengers (name, ID, seat, notes; each infant after the passenger whose seat they share) paginated like the cargo, the head count, ticket price and fares, and the carrier's and driver's signatures.
  - **Pagination** (`usePagedRows.ts`): the manifest renders a hidden copy of itself on one sheet with every cargo row, measures it (again once fonts load), and deals the rows out: page 1 opens with the vehicle, trip and parties table, later pages are titled "(تابع)" and repeat the cargo table header, and the total row, financial section and signatures stay together on the last page with at least one row above them.
  - The barcodes come from `bwip-js` (imported as `bwip-js/node`), rendered as SVG by the API (the main process in the demo).
- **QR code** (`verifyUrl` in `packages/shared/src/billing.ts`): a link to the public verify page, `<SITE_URL>/verify/<certificates.qr_token>` (32 random hex characters), the same on both documents. The desktop demo still encodes its old JSON payload.
- **Verify page** (`apps/site/src/pages/VerifyPage.tsx`, `VerifyApp.tsx`; `GET /verify/:token`, `services/verify.ts`): public, no sign-in, and it never redirects (an officer may or may not be signed in). It shows **Valid** until the certificate's `valid_until`, then **Expired**, with the MNF / PSG and MSR numbers, plate, trip type, route, departure and estimated arrival, carrier, taxes and fees paid and issue date, plus when it was checked. A passenger trip shows its **head count** instead of the trip type ("48 passengers, 3 infants"), for the officer to compare with the bus. Only paid bills' certificates are found; an unknown or malformed token shows "No manifest found". **No sender, receiver, driver or passenger names or IDs** leave the API. The route allows 60 checks a minute per IP (`http/rateLimit.ts`, in memory).

## Government dashboard & demo data

- **Dashboard** (`apps/api/src/services/dashboard.ts`, UI in the govt portal's `components/govt/`): the Government portal opens on an overview across all transport companies (`govt.dashboard`).
  - **Where the revenue figures come from**: without a trip filter, from the **daily revenue summary** (`daily_revenue`, `services/dailyRevenue.ts`): per Sudan day and dimension (total, category, cargo slice, charge, route, origin and destination state, company, vehicle type, trip kind). `refreshBillStatus` adds a trip's rows (`addPaidTrip`) in the transaction that records its payment (only the refresh that actually flips it to paid); demo seeding, regenerating and the load seeder rebuild it (`rebuildDailyRevenue`); migration 0006 filled it with the same SQL (`summarySql`). With a filter, the figures are grouped SQL over the paid trips (`liveFigures`); nothing loads rows into the API. A test checks both give the same numbers. Anything that writes payments in bulk must rebuild the summary.
  - **Filters** (`packages/shared/src/analytics.ts`, `AnalyticsFilters`): a period (presets 7 / 30 / 90 days, 12 months, this year, or custom dates, both days included) plus origin and destination (a city or a whole state), cargo type (any item of the trip), trip kind (cargo or passengers), vehicle type, trip type and transport company. `services/analyticsQuery.ts` turns them into conditions (`inFilteredTrips`); the dashboard, the report, the data export reuse it. The filter bar is `AnalyticsFilterFields.tsx`, shared with the export dialog.
  - *Revenue collected*: paid payments (taxes and fees) by `paid_at` in the period, with the % change vs the previous period of the same length (hidden when the records don't reach back that far).
  - *Active trips*, *Pending bills* and *Registered vehicles* aren't limited to the period, but the other filters apply (vehicles follow only the vehicle type and company filters).
  - *Collection rate*: paid ÷ billed amount for bills issued in the period.
  - Revenue chart: grouped by day / week (starting Sunday) / month, chosen by the user or picked from the range length (`resolveBucket`, at most 400 points). The last bucket is drawn dashed only when the period runs up to now.
  - *Revenue by cargo type* splits each trip's taxes across its items in proportion to their cost; passenger trips are one slice of their own (`PASSENGERS_SLICE`). *Revenue by tax and fee* sums the paid trips' `manifest_charges` lines by code, under the name of the latest bill.
  - The **breakdown card** groups revenue by route, origin state, destination state, cargo type, vehicle type, trip type, trip kind or transport company (`DashboardView.breakdown`, computed by the API) and sorts it by revenue, trips or name in the portal (`breakdownRows.ts`: top 9 plus "Others").
- **Search** (`services/govtTrips.ts`, `GovtSearchBar` / `GovtSearch`): one box above the government sections (`govt.search`) finds trips of every company by E-Sali bill ID (or its first 6+ digits), `MNF-…` / `PSG-…` / `MSR-…` number (whole or partial), trip number (`#123`), a passenger's **exact national ID or passport number** (one lookup in `trip_passengers_id_number_idx`), plate in either script and with Western or Arabic digits (`plateSearchKey`; a digits-only query also matches plates), registration, company, driver, sender, receiver or city name, plus an optional origin / destination. Newest first, **paged by the API** (`GET /govt/search`, `ui/Pagination.tsx`; a new search starts on page 1). Every condition is on the trip's own columns, so indexes serve it: small tables (vehicles, companies, cities, passengers' IDs, payments, certificates) are matched first as `column = ANY(ARRAY(subquery))`, names through trigram indexes (`pg_trgm`), prefixes through `text_pattern_ops` indexes. The count stops past **1,000** (`SEARCH_CAP`): the page says `more`, the portal shows "1,000+" and the pages stop there.
- **Read-only trip view**: a search result or a dashboard bill opens `TripDetails` with `readOnly` (`GET /govt/trips/:id`: `getTripDetails(null, …)`, any company). It shows the company, the branch and who booked it (name and phone), hides every company action, and previews attachments (the same `DocumentPreview`, from `GET /govt/documents/:id/file`) and the receipt and manifest. The dashboard and the results stay mounted (hidden) behind it, so going back keeps their state.
- **Exports** (*Export* on the dashboard, `ExportDialog.tsx`), prefilled with the dashboard's filters. Exports are always in Arabic.
  - **Report (PDF)** (`ReportModal.tsx`): A4 sheets with the letterhead (`DocumentSheet` without barcode or QR). Page 1 has the parameters, key figures, revenue chart (fixed size, Arabic) and trip progress; page 2 has revenue by cargo and by tax and fee, and the breakdown. The user picks the chart grouping, breakdown and sort, and which sections to include. *Print or save as PDF* opens the browser's print dialog once the chart has drawn, suggesting `masarat-report-<dates>` as the file name (`govt:save-report-pdf` in the demo).
  - **Data (Excel / CSV)** (`services/exports.ts`, `packages/shared/src/exports.ts`): trips (with departure, arrival, kind and ticket price), bills & payments, cargo items, **passengers** and tax & fee lines. Passengers' ID types and numbers are only written with *Include passengers' ID numbers* (`includeIdNumbers`, off by default: personal data in files that get passed around). The period applies to the trip date, the bill's issue date or the payment date, with a trip status filter. Excel (exceljs) gives one right-to-left sheet per dataset with a frozen bold header; CSV is UTF-8 with a byte order mark, one file per dataset. Excel and CSV can be chosen together. **Exports stream**: the rows are counted first (an Excel sheet past 1,048,575 rows, `EXCEL_MAX_ROWS`, is refused with `export_too_large_for_excel` and the counts, so the user picks CSV or a shorter period), then the trips are read in keyset batches of 5,000 (`exportLimits`) and written as they come to `<STORAGE_DIR>/exports/<random>` (CSV in one pass, Excel through exceljs's streaming writer, a sheet per pass). Items, passengers and tax lines follow the trips' departure order. Export queries get `EXPORT_STATEMENT_TIMEOUT_MS`. `POST /govt/exports` streams one file as is, or several as one `masarat-export-<dates>.zip` (fflate, written to disk), with the row counts in `X-Export-Rows`, and removes the folder once sent (leftovers go at startup and after an hour); the browser saves it (in the demo, several files went into a chosen folder). The options are checked (`isAnalyticsFilters`, `isExportOptions`) before anything runs. The export dialog has no company filter: exports cover every company. Headers and value labels come from the portal's Arabic translations (`export.columns.*`); plates stay in their stored form, amounts are numbers.
- **Demo data** (`apps/api/src/services/demoData.ts`): only in demo mode (`DEMO_MODE=true`, never in production). On startup, if there are no demo companies (`companies.is_demo`), the 4 demo companies of `DEMO_COMPANIES` (`packages/shared/src/demo.ts`) are created with their roles, 2–3 branches each (in cities on their routes), a company admin, an accountant and a clerk per branch, and about a year of trips, bills (with matching `esali_sim_bills` rows), payments and certificates, using the real trip cost and the taxes and fees as they are when it's seeded. A trip is booked at the company's branch in its origin city if it has one, otherwise at any of its branches, by that branch's clerk. Each trip gets 1–4 cargo items with Arabic names, and about a quarter of tanker trips carry liquids. Some loads are mixed: about 15% of big-truck trips carry a container, and about 10% of fuel tanker trips carry liquids. It is deterministic (fixed PRNG seed, dates relative to today). Each company has an address and TIN, each vehicle a registration number, and 5–8 drivers with Arabic names. Each trip also gets a trip type (imports and exports mostly on Port Sudan routes), sometimes trailers (big trucks), a driver, an Arabic sender and receiver, and packing details per item, and billed trips get the carrier details. All of these come from a second PRNG stream so the trips themselves stay the same. Each company also gets 1–2 **buses** (45–50 seats) with a template for its usual route, and passenger trips on the intercity routes on about 40% of days (mostly full, about 6% with an infant, 5% passport holders), from a third PRNG stream so the cargo trips stay the same; trucks leave between 05:00 and 20:00 and arrive at 50 km/h, buses at 70 km/h. Demo users have `users.is_demo = true`. The Government portal's hidden *⋯ → Regenerate demo data* deletes the demo companies and everything under them (including anything added by hand to one: its trips, members, roles and branches, and their sessions), then reseeds; other companies' data and the demo government accounts are kept.
- **Demo accounts** (`DEMO_COMPANIES`, `DEMO_GOVT_ACCOUNTS`; the login page lists `DEMO_ACCOUNTS` in demo mode, and clicking one fills the form). Everyone in a company has the company's password:
  - Government: `ministry.demo` (admin) and `ministry.agent` (agent), both `govt2026`
  - Company admins: `nile.transport` / `nile2026`, `redsea.logistics` / `redsea2026`, `kordofan.haulage` / `kordofan2026`, `gezira.freight` / `gezira2026`
  - Accountants: `<company>.accountant` (`nile.accountant`, …); clerks: `<company>.clerk1` … one per branch (`nile.clerk1` at مكتب بحري, …). The login page lists the admins, `nile.clerk1` and `nile.accountant`.
- **App version**: a grey badge in the header shows the portal's `package.json` version (`__APP_VERSION__`, set in `vite.config.ts`). In the demo it's `app.getVersion()` next to the MVP badge.
- Charts use **Recharts** (lazy-loaded) for the time series; ranked bars are plain HTML so they follow RTL. Charts keep time left → right in Arabic, with the value axis on the right.

## Planned: document review (not built)

OCR is out: whether a real OCR or document AI service is integrated is still under debate, so attachments are only uploaded and previewed. Instead, review will most likely be done by people:

- A new, **lower government role, the reviewer**, reviews the supporting documents trips were submitted with, and the manifests already issued. They can approve, decline or **report** one.
- If a reviewer suspects something, they may report it to a higher government role, or **decline / revoke the clearance**. The verify page then shows that the trip is **not cleared to travel**, so an officer scanning the QR code stops it.
- Later, with the SMS integration, a revocation notifies the driver and the company.
- Issuing may later depend on the review (no clearance before approval). **For now, issuing stays as it is**: payment issues the receipt and manifest straight away, and review only acts afterwards.

Keep the code ready for it: the verify page's status and the documents' lifecycle should be able to gain a "revoked" state without reshaping them.

## Tech stack

**BHVR**: Bun (runtime and package manager), Hono, Vite, React 19. TypeScript everywhere, Tailwind v4, Recharts, i18next.

- **Use bun only, never npm or npx**: `bun install`, `bun run <script>`, `bunx <bin>`, `bun add` inside the workspace.
- Bun blocks dependency install scripts unless the package is in `trustedDependencies`.
- The database is **Postgres + Drizzle ORM** through **postgres.js** (`apps/api/src/db`, config in `apps/api/drizzle.config.ts`, migrations in `apps/api/drizzle`). Locally it runs from `compose.yaml` (Postgres 18 on port **5433**, so it doesn't clash with another Postgres on 5432) with `bun run db:up`.
  - **Time limits**: Postgres stops an API query after `STATEMENT_TIMEOUT_MS` (15 s; it answers `query_timeout`, 503), Bun closes a silent request after `REQUEST_TIMEOUT_S` (30 s, `idleTimeout` in `index.ts`; exports and demo regeneration lift it with `liftRequestTimeout`). Migrations, the test setup and seeding run on `openUnlimitedDb()` or `SET LOCAL statement_timeout = 0`. New long-running work must do the same.
  - **Indexes on big tables**: migrations run in one transaction, so `CREATE INDEX CONCURRENTLY` isn't possible through `db:migrate`, and a plain `CREATE INDEX` blocks writes to its table while it builds. On a database with real volume, run such migrations in a **maintenance window** (`0006` fills `manifests.company_id` and builds about twenty indexes; on a year of national data that takes many minutes). An index can be built beforehand with `CONCURRENTLY` only if its columns already exist and its migration is written to reuse it: `0007` keeps a prebuilt index only when it is valid (`pg_index.indisvalid`) and its definition matches exactly, and builds it otherwise, so a fresh database still works. `0006`'s indexes on `company_id` can't be prebuilt (the column comes with that migration), and its other `CREATE INDEX` statements would fail on a prebuilt index of the same name.
  - Every query is async. One row is `const [row] = await …limit(1)`. A check-then-write that must not race runs in `db.transaction(async (tx) => …)` and locks the row with `.for('update')` (see `lockedStatus` in `services/trips.ts`).
  - Text enums are `text` columns with a CHECK each (`inList`), not Postgres enums, so adding a value is a plain migration.
  - Migrations are a deploy step (`bun run db:migrate`), never run by the API at startup. `0000_init.sql` is generated; `0001_reference_data.sql` is a custom migration (`drizzle-kit generate --custom`) seeding Sudan's 18 states (English and Arabic names, without "ولاية", and each one's capital) and 65 cities, the cargo rates, the default taxes and fees, and the government's two roles. `0002_charges.sql` creates `charges`, `charge_changes`, `manifest_charges` and `pricing_rates` and copies the old tax tables into them (bills keep their lines, now with names); `0003` drops the old tables. `0004_passenger_trips.sql` adds buses, passengers, templates, settings and `departure_at` / `arrival_at` (filled from the trip date, arriving at 50 km/h), and gives clerks `templates.use`; `0005` drops `trip_date`. `0006_scale.sql` (from the load test) enables `pg_trgm`, adds `manifests.company_id` (filled from the vehicles), the indexes the dashboard, lists, search and exports need, and `daily_revenue` (filled from the paid bills); `0007` indexes trips by origin and destination city with the departure. A table or column replaced in one migration would make `drizzle-kit generate` ask whether it was renamed: add the new one and copy in one migration (editing a generated NOT NULL column into add, fill, then set NOT NULL), drop the old one in the next. Cities point to their state (`cities.state_id`); the portals show a state's name from the reference data (`format.state`), not from the translations.
  - Always read a generated migration before committing it. Renaming a column makes `drizzle-kit generate` ask an interactive question, which can't be answered here: write that migration by hand (`--custom` with `ALTER TABLE … RENAME COLUMN`) and update the schema to match.
  - Tests (`bun run test`) use their own `masarat_test` database, created and migrated by `apps/api/test/setup.ts`.
  - **Sudan time**: `config.ts` sets `TZ` (default `Africa/Khartoum`) and the Postgres session uses the same zone. Departures and arrivals are local times and months group in local time, as on the desktop, whatever the host's zone.
  - The migrations were **rebased on 2026-11-22** (companies and roles; there was no real data): a database from before needs dropping and migrating again.
  - When the shape of trip data changes, the migration deletes the **demo companies and everything under them** (their trips, bills, payments, certificates, `esali_sim_bills`, vehicles, drivers, members, roles and branches), so the next startup reseeds them in the new shape. **Other companies' data is always migrated, never deleted**: new columns start empty, bills already issued keep their lines and amounts, and copies in table rebuilds must keep every existing row.
- Prettier skips `**/drizzle`, so it never reformats the migration snapshots.
- The web apps reach data only through `@masarat/api-client`, never the database.

## Commands

All from the repo root:

- `bun install`
- `bun run db:up` / `db:down` (local Postgres), `bun run db:migrate`, `bun run db:generate` (new migration from `schema.ts`)
- `bun run dev`: the API and the three web apps together. Or one at a time: `bun run dev:api` (port 3000), `dev:site` (5175), `dev:owner` (5173), `dev:govt` (5174). Open http://localhost:5175 to log in.

- `bun run dev:demo`: the Electron demo. Run `bun install` in `apps/desktop-demo` first, since it isn't a workspace.
- `bun run typecheck`, `bun run test` (API), `bun run build` (the three web apps), `bun run lint`, `bun run format`
- **Load test** (`loadtest/`, see its README): `loadtest/stack.sh` runs a separate Postgres (port 5434) and the API (port 3100) pinned to set CPUs, `bun run --filter @masarat/api load:seed` fills it with national-scale data (only a database named `*load*`), and `loadtest/run.sh` runs the k6 scenarios at a server size and load. `DB_POOL_MAX` sets the API's Postgres pool (default 10).
