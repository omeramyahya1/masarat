# Masarat

## What this is

Masarat is an electronic transport, manifests, and tax-collection system tailored for Sudan. Its goal is to improve how transport taxes are paid and collected.

It started as an **Electron MVP / demo** for the relevant government agency (kept, frozen, in `apps/desktop-demo`). We are now building the **production web version**. External integrations (E-Sali, banks) are still **simulated** behind interfaces. OCR was removed: government staff review clearances instead (see _Government review_).

## App shape

Three web apps and one API, each on its own (sub)domain:

1. **Site** (`apps/site`, `masarat.com`): the public landing page, **login for everyone**, company sign-up, the forced password change, and the public **verify page** a manifest's QR code opens. A signed-in user is sent to their portal (except from the verify page).
2. **Company portal** (`apps/owner-portal`, `owner.masarat.com`; the folder and subdomain keep their old names for now): used by **transport companies** (شركات النقل) and their staff. It has the trips, vehicles, drivers, profile and, by permission, _Team_, _Branches_ and _Roles_.
3. **Government portal** (`apps/govt-portal`, `govt.masarat.com`): used by government staff. It has the dashboard, search, exports and, for government admins, _Taxes and fees_ and _Users_.
4. **API** (`apps/api`, `api.masarat.com`): one Hono app on Bun that all three call.

The Electron demo showed both panels in one window with a toggle. The web apps don't: the account's kind (`users.kind`: `company` or `govt`) decides the portal.

**Terms**: a _transport company_ (code: `company`; "fleet owner" in the MVP) signs up, owns vehicles and drivers, and books trips at its _branches_. Its people are _members_, each with a _role_. The government's people are _users_ of the government portal, with a government role.

## Login and sessions

- **One login, on masarat.com** (`apps/site`): username and password only; the account's kind picks the portal. After login the site goes to `?next=` when it's a page of the user's own portal (`destinationFor` in `packages/ui/src/lib/urls.ts`; anything else would be an open redirect), otherwise to the portal's home. A signed-in user who opens masarat.com is sent straight on.
- **The portals have no login page.** `AppShell` asks `GET /auth/me`; without a session it sends the browser to `masarat.com/login?next=<this page>`, a user of the other kind to their own portal, and a user with a temporary password to `masarat.com/change-password`. Any API call that answers 401 fires `SIGNED_OUT_EVENT` (`@masarat/api-client`), which does the same. Logout returns to masarat.com.
- **Sessions** (`services/sessions.ts`, `sessions` table): a random 32-byte token in the `masarat_session` cookie (HttpOnly, SameSite=Lax, Secure over HTTPS, `Domain=COOKIE_DOMAIN` = `.masarat.com` in production so every subdomain sends it; unset locally, where one host-only cookie on `localhost` covers every port). Only the token's SHA-256 is stored. A session ends after **2 h idle** or **12 h** in all, and at once when the account is disabled or its password reset. Changing your own password signs out your other sessions. Expired rows are purged on startup and hourly.
- **Passwords**: Argon2id (`Bun.password`). Older scrypt hashes still verify and are rehashed at the next login.
- **Rate limit** (`login_attempts`): 5 failures per username or 20 per IP in 15 minutes give `too_many_attempts`. A wrong password and an unknown username answer the same (`invalid_credentials`, timed alike); `account_disabled` is only told after the password checks out.
- **CSRF and CORS** (`src/http/middleware.ts`, `src/app.ts`): requests that change something must carry an `Origin` that is one of `SITE_URL`, `OWNER_URL`, `GOVT_URL`; CORS allows exactly those, with credentials.
- **Sign-up creates a transport company** (`signUp` in `services/auth.ts`, `createCompany` in `services/companies.ts`): the company (name required, address and TIN optional), its three built-in roles, and the person signing up as its **company admin**. Government accounts are never self-made.
- **Accounts are managed by admins** (`services/members.ts`, one set of rules for both sides; UI `packages/ui/src/components/members/TeamPanel.tsx`): a company admin in Company portal → _Team_ (`/members`), a government admin in Government portal → _Users_ (`/govt/users`). Create (a 12-character temporary password shown once, a role and, for a branch role, the branch), disable / enable, reset password, change role / branch. An admin can't change their own account there, and each side always keeps one active admin (`last_admin`; the admins' rows are locked, so two admins demoting each other at once can't both succeed). Accounts with a temporary password (`must_change_password`) can only call `/auth/me`, `/auth/change-password` and `/auth/logout` until they pick their own. One person belongs to one company.
- **There is exactly one government admin** (migration 0010's unique index `users_one_govt_admin_idx`; `admin_exists`). It comes from the server: `bun run --filter @masarat/api user:create-admin <username> <phone> "<full name>"` prints its temporary password (`scripts/createAdmin.ts`, `createOrUpdateAdmin`).
  - With `APP_ENV=production` the command only creates the admin when there is none; replacing it means taking the role from the current admin by hand first (`docs/deployment/predeployment-checklist.md`).
  - In development it upserts: the existing admin gets the given username, phone and name, a new temporary password, is enabled again and signed out.
  - The _Users_ screen never offers the government admin role (`GET /govt/users/roles` leaves it out), and creating or promoting another admin answers `admin_exists`.
  - The demo seeds `ministry.demo` as the admin only when the database has no admin yet.
- **Roles and permissions** (`packages/shared/src/permissions.ts`): the typed lists `COMPANY_PERMISSIONS` (`trips.view`, `trips.edit`, `trips.bill`, `templates.use`, `templates.manage`, `fleet.view` / `.manage`, `drivers.view` / `.manage`, `company.profile`, `branches.manage`, `members.manage`, `roles.manage`) and `GOVT_PERMISSIONS` (`govt.dashboard`, `govt.search`, `govt.exports`, `govt.charges`, `govt.settings`, `govt.users`, `govt.reports.create`, `govt.reports.review`) are the single source: the `role_permissions` CHECK is built from them (a test checks it), routes declare what they need with `requirePermission(...)` (any of), and the portals ask `useCan()(…)` (`packages/ui/src/lib/account.tsx`) to show only what the user can use. Doing implies seeing (`withImplied`: `fleet.manage` adds `fleet.view`, `govt.reports.review` adds `govt.reports.create`, …).
  - A role (`roles`) has a name, a **scope** (`branch`: the member works at one branch, `users.branch_id`, and sees and books only its trips; `company`: every branch) and its permissions (`role_permissions`). Built-in roles have a `key`.
  - Every company starts with **company admin** (locked, every company permission, from the code), **clerk** (branch: view, book and bill trips, and book from templates) and **accountant** (company-wide: view and bill trips, view vehicles and drivers). The clerk and accountant can be edited; a company adds its own roles with checkboxes in _Roles_ (`services/roles.ts`; a role in use can't be deleted or change scope).
  - The government has three **fixed**, locked roles (no `company_id`; `GOVT_ROLE_KEYS`, highest first): **government admin** (everything, including _Taxes and fees_, _Settings_, _Users_ and _Reports_), **government supervisor** (dashboard, search, exports, and reporting and reviewing clearances: `govt.reports.create`, `govt.reports.review`) and **government agent** (dashboard, search, exports, and reporting a clearance: `govt.reports.create`). _Users_ offers the supervisor and the agent (in that order), never the admin. See _Government review_.
  - Each request loads the account with its company, role, branch and permissions (`accountOf` in `services/access.ts`), so a role change takes effect on the next request. `/auth/me` returns it (`AuthUser`).
  - **Scope in the queries**: the company services take a `CompanyScope` (`{ companyId, branchId | null }`, from `scopeOf`), the government's read-only views `null`; `tripScopeCondition` adds `manifests.company_id` (the vehicle's company, kept on the trip so company lists read one index, `(company_id, departure_at)`), or for a branch member `manifests.branch_id` alone (a branch is one company's, so `(branch_id, departure_at)` answers counts by itself), to every trip query, so another company's or branch's trip answers 404. Every new trip sets `company_id` (`createTrip`, the demo and load-test seeders).
- **Phone numbers** (`packages/shared/src/phone.ts`): every account (company members, government users) and every driver has a **Sudanese mobile number**, for SMS later (one-time codes, notifications). `normalizeSudanPhone` accepts `0912345678`, `912345678`, `+249…`, `00249…` or `249…` with spaces or dashes, takes mobile numbers starting with 9 or 1, and stores `+249912345678`; `formatSudanPhone` shows `+249 91 234 5678`. An account's number is unique across all accounts (`users_phone_unique`, `phone_taken`); a driver's is unique among the company's drivers. Senders' and receivers' phones may be foreign (`normalizePhone` in `fleet.ts`).
- **Language**: every site opens in **Arabic** unless the user picked English. The choice is the `masarat_lang` cookie (a year, on `VITE_COOKIE_DOMAIN` = `.masarat.com` in production, so the three sites share it; host-only `localhost` locally), set in `packages/ui/src/i18n/index.ts`. Missing keys fall back to English.
- **Demo mode** (`DEMO_MODE=true`, never in production): seeds the demo data, shows the demo accounts on the login page (`GET /config`), and allows the demo-only actions (simulated payment, regenerate demo data).

## Production status

Login, both portals and the verify page work end to end on Postgres.

- **Both portals are wired** to the API (`apps/api/src/routes/`, listed in `apps/api/ROUTES.md`): the company's `/vehicles`, `/drivers`, `/trips`, `/documents`, `/company`, `/branches`, `/roles`, `/members`, and the government's `/govt/*`. Each route takes the account from the session (`c.get('user')`, an `AuthUser`), checks its permission, and passes its company scope to the service (`null` for the government's read-only views of any company).
- `@masarat/api-client` follows the old `window.api`, except where the desktop did things natively: files are uploaded (`documents.upload`) and fetched as blobs (`documents.file`, `govt.documentFile`), exports come back as a file to save (`lib/saveFile.ts`), and documents and the report print from the browser. CORS exposes `Content-Disposition` and `X-Export-Rows`, so the client can read a download's name and an export's row counts.
- **Deployment**: `docs/deployment/` has the architecture, the pre-deployment checklist, the backup plan and the sizing.
  - **The API is stateless**, so it runs as several instances behind a load balancer:
    - attachments live in **S3-compatible storage** (MinIO, `services/storage.ts`)
    - upload staging, the verify page's rate limit and the export queue live in **Redis** (`services/redis.ts`)
    - everything else is in Postgres
    - data exports are built by the **export worker**, a separate process (see _Exports_), never by the API instances
    - a Bun process runs its JavaScript on one core, so a server runs one API process per CPU, sharing the port (`REUSE_PORT=true`; Linux spreads the connections)
  - **Overload** (`http/loadShed.ts`): an instance handles at most `MAX_IN_FLIGHT` (200) requests at once; past that it answers `503 server_busy` with `Retry-After` at once, before the session's query, instead of queueing for a Postgres connection while its user gives up. The health checks are never refused.
  - The API runs on Sudan time (`TZ=Africa/Khartoum`, see Tech stack).
- **Logs** (`src/log.ts`, `http/requestLog.ts`): pino JSON lines to stdout and to daily files in `LOG_DIR`, deleted after `LOG_RETENTION_DAYS` (7) by the `logs.cleanup` job.
  - Every request gets an `X-Request-Id` (the proxy's, or a new one), returned on the response and on every line it causes, through `AsyncLocalStorage`. Use `log.info/warn/error(message, fields?, err?)` anywhere.
  - One access line per request (route, status, ms, user, company).
  - An unhandled error's reply carries `requestId`.
  - Passwords, tokens, cookies and ID numbers are redacted.
- **Health**: `GET /health` (alive) and `GET /health/ready` (Postgres, Redis and the bucket answer; 503 otherwise, and while stopping). On SIGTERM / SIGINT the API stops taking requests, lets the ones in flight finish (`SHUTDOWN_GRACE_MS`, 25 s), stops the jobs and closes its connections.
- **Background jobs** (`services/jobs.ts`, scheduled in `index.ts`): `sessions.purge` (hourly), `uploads.sweep` (daily), `trips.archive` (hourly, works 01:00–05:00), `dashboard.aggregate` (hourly, once a day from 01:00), `logs.cleanup` (daily, every instance). The others run on one instance at a time (`pg_try_advisory_xact_lock`). The export worker runs `exports.sweep` (expired export files, every 10 minutes) and its own `logs.cleanup`.
- **Production config fails fast** (`buildConfig` in `config.ts`): with `APP_ENV=production` the API refuses to start:
  - with a setting left to its development default
  - with `DEMO_MODE=true`
  - with an http `SITE_URL`
  - when `DATABASE_URL` is the owner's
- **Security headers** on every API response (`hono/secure-headers`: HSTS over HTTPS, nosniff, `frame-ancestors 'none'`, `no-referrer`, CORP same-site). The web apps' own headers (CSP, …) are the static host's job (checklist).
- **The data model is being revised.** The rules below describe the behaviour carried over from the MVP.
- IPC channel names in the rules below (`documents:pick`, `govt:get-trip`, …) are the demo's, and each one becomes an API route. Anything the desktop did with native dialogs or `printToPDF` (picking files, opening files, saving PDFs, export save dialogs) still has to be redone for the browser. On the API side that's already started: uploads go through `stageDocument`, and `exportData` returns the files.

## Core flow (transport company)

1. **Log in.**
2. **Create a new trip** with its details: the vehicle, the route, the departure and estimated arrival, and what it carries: **cargo** (a truck or tanker) or **passengers** (a bus).
3. **Tax calculation**: the system computes the tax due for the trip.
4. **Bill generation**: the app simulates an **E-Sali (Esali) API** call that returns a **bill ID**.
5. **Payment**: the user pays that bill ID through **Bankak** or another bank. The MVP simulates this.
6. **Payment confirmation**: once the system confirms payment, it moves on to the next step.
7. **Documents**: the app issues the **electronic payment receipt** and the **authorized manifest** (تصريح الحركة), each with a barcode of its number and a **QR code** that traffic/checkpoint **officers can scan to verify it quickly**.

## Fleet & trips rules

- **Plate numbers** (`packages/shared/src/plate.ts`): a state code of 1-2 letters (KH, RS, NK, …), a series from 1 to 99, then a number from 1 to 99999. They are stored in English as `"KH 12/34567"` and shown in Arabic as `"خ ١٢ / ٣٤٥٦٧"` (letters → series → number, read right to left), with Eastern Arabic digits. Validation happens in the UI and services, not as a DB constraint.
- **Digits**: plates are the only thing shown with Eastern Arabic digits (badge, plate text, plate inputs). Every other number, amount and date uses English digits, even in the Arabic UI. Stored and backend values are always English.
- **Pricing is a development formula** (`services/pricing.ts`, the `PricingService` interface): how cargo and tickets are really priced isn't known yet. `FormulaPricing` uses `pricing_rates`: a rate per km for each cargo type, and **80 SDG per km per seat** for a passenger ticket (`calculateTicketPrice`; Khartoum → Port Sudan ≈ 875 km ≈ 70,000 SDG). **`APP_ENV`** (`development` | `production`, in `config.ts`): with `APP_ENV=production` the API refuses to start while trips are priced by the formula (`assertPricingAllowed` in `index.ts`), so a real `PricingService` has to replace it first. Trip saving and billing price through `pricing`, never the tables directly.
- **Trip cost** (`calculateItemsCost` in `packages/shared/src/tax.ts`): the sum of the cargo items' costs. Each item costs `rate_per_km × distance_km × quantity / per_quantity` at its own cargo type's rate (`pricing_rates`), with its quantity in the rate's unit. Items keep a snapshot of the rate and their cost. Distance is the haversine distance between the cities × a 1.3 road factor (an estimate until real routing exists).
- **Taxes and fees ("charges")** (`charges` table, `calculateCharges` in `packages/shared/src/tax.ts`): one list, each charge a **percentage** of the trip cost (`kind = 'percent'`, in basis points, 1700 = 17%) or a **fixed amount** in whole SDG (`'fixed'`, not taxed).
  - Each charge has its own value for **cargo trips** and for **passenger trips** (`cargo_value`, `passenger_value`); null means it isn't charged on that kind of trip. It can be switched off (`active`).
  - Four are built in (`BUILTIN_CHARGE_CODES`, `builtin`): VAT (17%), business profit tax (3%), locality tax (2%) and the **manifest fee** (رسوم المنفيست, 1500 SDG), with the same values for both kinds. They can be renamed, changed and switched off, not removed. The admin adds **custom** ones (code `custom_<id>`).
  - Names are stored in both languages (`name`, `name_ar`), not in the translations; `format.chargeName` / `format.taxLine` pick the current language.
  - A bill's lines are the active charges with a value for its kind: the percentages first, then the fixed fees, each in list order (`sort`) and rounded to whole SDG; the total is their sum.
  - The **bill is the total of the taxes and fees** (`manifests.tax_amount`). The trip cost is shown for reference.
  - A trip's lines are kept in `manifest_charges` with the charge's code, **name and value at the time** (a fixed fee has `rate_bps = null`). Drafts are priced when saved, and _Generate bill ID_ reprices them at the current charges; from then on they're frozen, so renaming or changing a charge never changes a bill already issued.
  - A trip's kind (`manifests.category`: `cargo` or `passenger`) comes from its vehicle (`tripCategoryFor`: a bus carries passengers), and picks the charges' value.
  - The API recomputes cost and charges on save; the portal's preview is never trusted.
- **Settings** (Government portal → _Settings_, `services/settings.ts`, `GET|PUT /govt/settings`, `govt.settings`: government admins only; `system_settings`, one row per key): per kind of trip, how long documents stay **valid after the estimated arrival** (0–720 h, default 24) and the **average speed** the trip form suggests the arrival from (10–150 km/h, defaults 50 for cargo and 70 for passengers). A new margin applies to documents issued afterwards.
- **Taxes and fees screen** (Government portal → _Taxes and fees_, `services/charges.ts`, `GET|POST /govt/charges`, `PUT /govt/charges/:id`, `govt.charges`: government admins only): a table of the charges with their cargo and passenger values; _Add a tax or fee_ and the edit dialog set both names, the kind (fixed once created), each kind of trip's value or "not charged", and on / off. Percentages from 0 to 100% with up to 2 decimals, fees from 0 to 1,000,000 SDG; a charge needs a value for at least one kind (`invalid_charge`). Each changed field is logged in `charge_changes` (who, which field, old and new value as text). Approval comes later.
- **Profile** (_Profile_ section): every member edits their own name and phone (`PATCH /auth/profile`, `updateProfile`). Below it, the **company's details** (`PUT /company`, `updateCompany` in `services/companies.ts`, `company.profile`; read-only for others): name, address and TIN (الرقم الضريبي), the **carrier details** printed on its manifests. Sign-up also asks for the address and TIN (optional there). Limits: address up to 200 characters, TIN up to 30.
- **Branches** (_Branches_ section, `services/branches.ts`, `branches.manage`; every member can list them): where the company books trips, often a booth at a land port: a name (unique in the company) and a city. A closed branch keeps its trips and members but takes no new trips (`branch_inactive`).
- **Every trip is booked at a branch** (`manifests.branch_id`, and `created_by` the member who booked it). A branch member's trips are always their own branch's, whatever the form sends; a company-wide member picks the branch in the trip form (`branch_required`). Trips can be filtered and grouped by branch.
- **Vehicles and drivers belong to the company**, not to a branch (`company_id`). Seeing them needs `fleet.view` / `drivers.view` or `trips.view` (the trip form lists them); changing them `fleet.manage` / `drivers.manage`.
- **Vehicles** need a **registration number** (رقم الترخيص, `vehicles.registration_no`, up to 30 characters) when added or edited. It is null only for vehicles added before it existed; the vehicles list flags those.
- **Drivers** (_Drivers_ section, `services/drivers.ts`, `drivers` table): each company keeps a list of drivers with a name and phone. Phones are Sudanese mobile numbers (see _Phone numbers_) and are unique per company.
- **Manifest details** (what the authorized manifest prints): each trip has a **trip type** (`domestic` / `import` / `export`), up to 3 **trailer plates** (`manifest_trailers`, each different from the vehicle's plate), a **driver** from the company's list, and a **sender** and **receiver** (name, address, phone). Each cargo item also has a **packing type** (free text; common types in `PACKING_SUGGESTIONS` and the company's earlier ones are suggested), a **number of packages** and optional **notes**. Its quantity is shown as the **weight**.
  - Drafts can leave the driver, sender, receiver and packing details empty, but what is entered is validated.
  - _Generate bill ID_ needs `missingForBilling` (`packages/shared/src/fleet.ts`) to be empty: the driver, a complete sender and receiver, the packing type and package count on every item, and the company's address and TIN. Otherwise it returns `incomplete_manifest`, and the trip page lists what's missing.
  - The manifest keeps its own copy of the driver's name and phone (saved with the draft and refreshed when the bill is generated) and of the **carrier details** (the company's name, address and TIN, copied when the bill is generated).
  - A driver on a draft can't be deleted (`driver_in_use`); deleting one used only by billed trips sets their `driver_id` to null.
  - `trips:suggestions` returns the senders, receivers and packing types of the trips booked in the last 30 days (`SUGGESTION_DAYS`) for the form.
- **Supporting documents** (`services/documents.ts`, `trip_documents`, UI in the company portal's `trips/DocumentsField.tsx`): a trip can have one file per document type. The commercial invoice and packing list always apply, the certificate of origin for imports, and the import/export authorization for imports and exports (`documentTypesFor`). Files are PDF, JPG or PNG, up to 20 MB, and are optional.
  - _Attach_ opens the browser's file picker and uploads the file (`POST /documents`, multipart, its own 20 MB body limit; `documents:pick` in the demo). `stageDocument` checks the extension, size and first bytes (a renamed file of another kind is refused), and writes it to the bucket as `documents/<upload day>/<token>.<ext>` (`userData` in the demo), staged in Redis for 24 hours under its random token **with the uploader's id**: nobody else can attach it. Saving the trip records the object's key in `trip_documents.stored_name` (the object doesn't move) and consumes the token. The daily `uploads.sweep` deletes uploads of two days ago that no trip uses. `bun run --filter @masarat/api storage:migrate` copies attachments from the old disk layout into the bucket (once, after upgrading).
  - Drafts can add, replace or remove attachments; documents of a type the trip no longer needs (after its type changed) are dropped on save. Deleting a draft, or regenerating demo data, deletes its objects.
  - _View_ opens an attachment in an **in-page preview** (`trips/DocumentPreview.tsx`, both portals): PDFs in the browser's own viewer, images as they are, with _Download_ and previous / next (and the arrow keys, following the reading direction) through the trip's documents. The file comes as a blob from `GET /documents/:id/file` (`findOwnedDocumentFile`, sent inline with `nosniff` and `no-store`), so the API never has to allow being framed. In the demo, `documents:open` opened the system viewer.
- **Passenger trips (buses)** (`packages/shared/src/passengers.ts`, `trip_passengers`, UI `trips/PassengersEditor.tsx`): a `bus` is counted in **seats** (`capacity_unit = 'seat'`, whole numbers; only a bus is). Its trips are always **domestic** (they change buses at the border), have no trailers, sender, receiver or documents, and carry **passengers** instead of cargo items.
  - Each passenger: name, ID (**national ID**, 11 digits, or **passport**, 6–20 letters and digits; stored normalized, `normalizeIdNumber`), **seat** (1 to the bus's seats, one passenger per seat) and notes (nationality, …).
  - **People registry** (`people`): everyone who travelled with an ID, once for all companies, unique by `(id_type, id_number)`, with the name of their latest booking. A trip's passenger (`trip_passengers`) links to it (`person_id`; null for an infant without an ID) and keeps the **name as booked**, since the passenger manifest is an official document. Booking upserts the people (`upsertPeople` in `services/trips.ts`); IDs are read through the person (trip view, exports, the government search by ID). An **infant** on a passenger's lap shares their seat, has no ticket, may have no ID and is noted رضيع (`checkPassengers`, `seat_taken`, `invalid_passengers`).
  - **Ticket price** = the ticket rate per km per seat × distance (`pricing.ticketPrice`; 80 SDG/km in development); the **trip cost** = ticket price × tickets (everyone with a seat). `cargo_quantity` holds the tickets (unit `seat`), `cargo_type` is null, `ticket_price` the price. Billing reprices the ticket and the charges, then everything is frozen: **no late boarding** (`not_draft`).
  - A draft may have no passengers yet; _Generate bill ID_ needs at least one ticket and an ID for everyone with a seat (`passengers`, `passenger_ids` in `missingForBilling`).
  - The company's trips search finds a passenger by their whole name as booked, or their exact ID number, within the period shown.
- **Departure and arrival** (every trip): `manifests.departure_at` and `arrival_at` (the estimate), entered as local date and time (`YYYY-MM-DDTHH:MM`, `parseLocalDateTime`). The form suggests the arrival as departure + distance ÷ the government's average speed for the kind of trip, rounded up to the quarter hour (`suggestedArrival`), until the member types their own; it must be after the departure (`invalid_arrival`). Filters, sorting and month groups use the departure.
- **Trip templates** (`services/templates.ts`, `/templates`, _Templates_ section with `templates.manage`; listed with `templates.use`, a branch member sees their branch's): a passenger trip a company repeats: name, branch, route, a bus, its usual driver, the time of day it leaves and how long it takes. _From a template_ in Trips opens the form with them filled in, leaving today (or tomorrow once the time has passed) and arriving after the duration.
- **List tools** (`ui/ListToolbar.tsx`): the company's Trips, Vehicles and Drivers lists have a search box, filters, sort with a direction toggle and, except drivers, group-by with a header row per group (trips show count and total due). The settings are kept per list in `sessionStorage`.
  - **Vehicles and drivers** load in full and filter in the browser (`lib/useListView.ts`).
  - **Trips are shown one period at a time** (`trips/PeriodBar.tsx`; `from` / `to` in `TripListQuery`, `resolvePeriod` in `services/tripList.ts`): the current month by default, with previous / next month and a custom range of at most `MAX_PERIOD_DAYS` (92; longer or reversed is `invalid_period`). Every count, group total, filter and the search cover that period only, so a query reads one range of the `(company_id, departure_at)` or `(branch_id, departure_at)` index. The page says which `period` it covers; `overall` is the period's trips before filters and search.
  - **Trips are paged by the API** within the period (`lib/useServerList.ts`, `GET /trips`, `services/tripList.ts`): numbered pages (`ui/Pagination.tsx`, 25 / 50 / 100 per page), the search debounced. The API filters and sorts. **The search matches whole names only**: the trip number (`#12` or `12`), the plate (either script, as part of it), a passenger's exact ID number, and a whole city, driver, sender, receiver, passenger or cargo item name, compared by the Postgres function `masarat_name_key` (migration 0008: case, spaces, tatweel, diacritics and the spelling variants أ/إ/آ→ا, ة→ه, ى→ي don't matter). The trips' names have their key **stored** (generated columns `driver_name_key`, `shipper_name_key`, `receiver_name_key`, `manifest_cargo_items.name_key`, `trip_passengers.full_name_key`, migration 0017), so a search computes the key once, for the text, and the matching cities are found first; computing it for every trip of the period cost about 8× more. A list page's rows carry their cargo items only (`toTripRecords(rows, 'list')`); a trip's page loads its passengers, tax lines, trailers and documents. Part of a name finds nothing. The government search keeps partial matching. **Grouping works across pages**: rows are ordered by their group first, each page shows the headers of its groups, and each header's count and total due cover the whole group (`groups` in the page). The portal labels the groups from their keys (status, `YYYY-MM`, vehicle id, driver id, `origin-destination` ids, trip kind, cargo type, branch id). The filters' vehicle, driver and branch options come from the company's lists; only company-wide members see the branch filter and group.
- New trips are saved as `draft` manifests. Until their bill ID is generated, drafts can be edited in the same form (_Edit trip_, `updateTrip`) or **deleted** for good, with their items and tax lines (`deleteTrip`). Otherwise both return `not_draft`.

## Billing & certificates rules

- **Flow** (`apps/api/src/services/billing.ts`, UI in `components/trips/TripDetails.tsx`): `draft` → _Generate bill ID_ → `billed` (shown as "Pending payment") → the user pays the bill ID from any banking app → _Refresh status_ → once E-Sali reports it paid, the payment is recorded, the receipt and the authorized manifest are issued (one `certificates` row) and the manifest becomes `certified` (shown as "Authorized"). Our `payments` row only changes on refresh. Afterwards a supervisor may turn `certified` into `revoked`, or `billed` into `cancelled` (its payment too); both are final (_Government review_). `refreshBillStatus` locks the trip first and never authorizes a cancelled trip (`trip_cancelled`), even if E-Sali reports its bill paid later; the demo payment refuses it too.
- **E-Sali bill ID** (`packages/shared/src/billing.ts`): `yyyy` `mm` `0dd` (day as 3 digits) + 13 random digits = 22 digits, e.g. `2026110170000123456789`. One bill per manifest; generating again returns the existing bill.
- **E-Sali is simulated** behind the `EsaliGateway` interface in `apps/api/src/services/esali.ts`. The mock keeps E-Sali's side in the `esali_sim_bills` table (simulation only; drop it with the real API). The hidden "⋯ → Pay <billId>" menu on a pending trip marks the bill paid at E-Sali.
- **Documents** (`certificates` table, `components/trips/CertificateModal.tsx`): issued together once the bill is paid, **valid until the estimated arrival plus the government's margin** for the kind of trip (`validUntilFor`, _Settings_, 24 h by default). Always rendered in Arabic (`i18n.getFixedT('ar')` + `createFormatters`), issued by ديوان الضرائب with the Sudan emblem (`assets/sudan-emblem.svg`, Wikimedia Commons). _Print or save as PDF_ opens the browser's print dialog (`lib/printDocument.ts`; the page title is set to the receipt number meanwhile, so _Save as PDF_ suggests it as the file name). The demo used `webContents.printToPDF`. The `@media print` rules in `main.css` (with `@page` A4, 10 mm) print only the dialog's sheets.
  - **Every page is a fixed A4 sheet** (`DocumentSheet` in `documentParts.tsx`, 190 × 276 mm inside the 10 mm page margin; `.print-sheet ~ .print-sheet` breaks the page). Each sheet repeats the letterhead (authority lines, emblem centred, and on the left the **Code 128 barcode** of the document number with the issue date) and a footer with the **QR at the bottom left** and "صفحة n من N". The barcode carries the MSR-/MNF- number itself, so there is no Arabic caption under it. `documentFrame.ts` builds what a document's sheets repeat.
  - **Page 1** (`ReceiptPage.tsx`) is the **electronic payment receipt** (إيصال سداد إلكتروني), number `MSR-<yyyy>-<manifestId 6 digits>` (`certificate_no`), with the trip cost and each tax and fee line. It fits one page.
  - Then the **authorized manifest** (`ManifestPage.tsx`) (تصريح حركة بضائع بري), number `MNF-<yyyy>-<manifestId 6 digits>` (`manifest_no`). It lists the vehicle, trailers, registration no., route and trip type; a table of the carrier, driver, sender and receiver; the cargo (description, packing, packages, weight, notes); the financial and customs section (قيمة الترحيل = the trip cost, رقم الإقرار الجمركي left blank); and name / signature / date / stamp blocks for the carrier, the driver (received the goods) and the receiver (on delivery). Customs, Zakat and others stamp the printed copy; that's out of scope. A typical trip fits one A4 page.
  - A passenger trip's manifest is the **passenger manifest** (`PassengerManifestPage.tsx`) (كشف ركاب), numbered `PSG-<yyyy>-<manifestId 6 digits>` (`manifestNoFor`), so an officer tells it from the number: the bus, route, departure and arrival, carrier and driver, then the passengers (name, ID, seat, notes; each infant after the passenger whose seat they share) paginated like the cargo, the head count, ticket price and fares, and the carrier's and driver's signatures.
  - **Pagination** (`usePagedRows.ts`): the manifest renders a hidden copy of itself on one sheet with every cargo row, measures it (again once fonts load), and deals the rows out: page 1 opens with the vehicle, trip and parties table, later pages are titled "(تابع)" and repeat the cargo table header, and the total row, financial section and signatures stay together on the last page with at least one row above them.
  - The barcodes come from `bwip-js` (imported as `bwip-js/node`), rendered as SVG by the API (the main process in the demo).
- **QR code** (`verifyUrl` in `packages/shared/src/billing.ts`): a link to the public verify page, `<SITE_URL>/verify/<certificates.qr_token>` (32 random hex characters), the same on both documents. The desktop demo still encodes its old JSON payload.
- **Verify page** (`apps/site/src/pages/VerifyPage.tsx`, `VerifyApp.tsx`; `GET /verify/:token`, `services/verify.ts`): public, no sign-in, and it never redirects (an officer may or may not be signed in). It shows **Valid** until the certificate's `valid_until`, then **Expired**; a revoked clearance shows **Revoked** (with the date, `revokedAt`, and that the vehicle isn't cleared to travel) whatever its validity; while a report is open it stays **Valid** with a **"Reported — under review"** band (`underReview`); a cancelled trip never had a certificate, so nothing is found. It shows the MNF / PSG and MSR numbers, plate, trip type, route, departure and estimated arrival, carrier, taxes and fees paid and issue date, plus when it was checked. A passenger trip shows its **head count** instead of the trip type ("48 passengers, 3 infants"), for the officer to compare with the bus. Only paid bills' certificates are found; an unknown or malformed token shows "No manifest found". **No sender, receiver, driver or passenger names or IDs** leave the API. The route allows 60 checks a minute per IP (`VERIFY_RATE_LIMIT`; `http/rateLimit.ts`, counted in Redis so every API instance shares it, and let through if Redis is down).

## Government dashboard & demo data

- **Dashboard** (`apps/api/src/services/dashboard.ts`, UI in the govt portal's `components/govt/`): the Government portal opens on an overview across all transport companies (`govt.dashboard`).
  - **How the portal gets it: nightly aggregates plus today** (`services/dashboardFacts.ts`, `dashboard_facts`, migration 0013).
    - **Nightly aggregates.** From 01:00, the hourly `dashboard.aggregate` job (one instance) computes every figure of each past day into `dashboard_facts`:
      - grain: day × origin city × destination city × kind of trip × trip type × vehicle type × **main** cargo type
      - row kinds: paid revenue, cargo shares, tax and fee lines, a per-company rollup (by kind of trip, trip type and vehicle type only), trips by status, bills issued and paid, documents issued
      - it recomputes the last `DASHBOARD_RECOMPUTE_DAYS` (35) days, where statuses and payments still change, plus any day not covered yet (a new database is filled from the whole history)
      - each month that's over is also added up into `dashboard_facts_month` (migration 0018; a month missing its rows is filled on the next run). The grain is fine enough that a day holds about as many fact rows as trips, so a long range reads its whole months there and only its first and last days from the daily facts (12 months with a filter: seconds → under a second); the revenue chart reads the days
    - **Two endpoints.**
      - `POST /govt/dashboard/history`: whole days before today, from the aggregates, with any day the job missed computed live, plus the previous period's revenue (whole days)
      - `POST /govt/dashboard/today`: today live, plus the present (`currentFigures`: active trips, pending bills, vehicles, companies, latest bills)
    - **The portal** (`GovtDashboard.tsx`, `dashboardData.ts`) adds the two together (`mergeDashboard` in `packages/shared/src/dashboard.ts`).
      - TanStack Query keeps the history until shortly after the next 01:00. _Refresh_ asks for today only. Today is fetched once, then on _Refresh_.
      - Exact figures to the minute aren't needed (availability over consistency): figures are as of their day's last aggregation.
      - The Redis cache keeps the history until the next aggregation and today for 30 s (`cachedHistory`, `cachedToday`).
      - Regenerating demo data and the load seeder reset and rebuild the aggregates.
    - **The breakdown by transport company** comes from the per-company rollup. With an origin, destination or cargo filter it isn't offered.
    - A test checks that history + today equal the live computation.
  - **The older full computation** (`POST /govt/dashboard`, `getDashboard`) is kept for the tests' comparison, but the portal doesn't use it.
    - Without a trip filter, it reads the **daily revenue summary** (`daily_revenue`, `services/dailyRevenue.ts`): per Sudan day and dimension (total, category, cargo slice, charge, route, origin and destination state, company, vehicle type, trip kind). `refreshBillStatus` adds a trip's rows (`addPaidTrip`) in the transaction that records its payment (only the refresh that actually flips it to paid); demo seeding, regenerating and the load seeder rebuild it (`rebuildDailyRevenue`); migration 0006 filled it with the same SQL (`summarySql`). With a filter, the figures are grouped SQL over the paid trips (`liveFigures`); nothing loads rows into the API. A test checks both give the same numbers. Anything that writes payments in bulk must rebuild the summary.
  - **Filters** (`packages/shared/src/analytics.ts`, `AnalyticsFilters`): a period (presets 7 / 30 / 90 days, 12 months, this year, or custom dates, both days included) plus origin and destination (a city or a whole state), cargo type (the trip's **main** cargo type, its costliest item's, the aggregates' grain; the old full computation and the exports use the same rule, `tripConditions`), trip kind (cargo or passengers), vehicle type and trip type. There is no company filter. `services/analyticsQuery.ts` turns them into conditions (`inFilteredTrips`); the dashboard, the report, the data export reuse it. The filter bar is `AnalyticsFilterFields.tsx`, shared with the export dialog.
  - **Cost and caching of the full computation**: about fifteen queries, run together (`Promise.all` in `getDashboard`), so it takes as long as the slowest. Its route serves it through `services/dashboardCache.ts` (`cachedValue`): each set of filters and view is computed once and kept in Redis for `DASHBOARD_CACHE_S` (60 s, shared by the API instances; identical requests on one instance share one computation); regenerating demo data clears it. Filtered views read live and archived trips through the `all_*` views, which costs about 2.4× a live-table query (a join of two UNION ALL views can't pair their halves).
  - _Revenue collected_: paid payments (taxes and fees) by `paid_at` in the period, with the % change vs the previous period of the same length (hidden when the records don't reach back that far).
  - _Active trips_, _Pending bills_ and _Registered vehicles_ aren't limited to the period, but the other filters apply (vehicles follow only the vehicle type and company filters). These counts read their indexes alone (`manifests(created_at, status)`, `payments(created_at, status, amount)`, pending bills' partial index); with a trip filter they join the trip by its key instead of `IN (…)` over every matching trip.
  - _Collection rate_: paid ÷ billed amount for bills issued in the period.
  - Revenue chart: grouped by day / week (starting Sunday) / month, chosen by the user or picked from the range length (`resolveBucket`, at most 400 points). The last bucket is drawn dashed only when the period runs up to now.
  - _Revenue by cargo type_ splits each trip's taxes across its items in proportion to their cost; passenger trips are one slice of their own (`PASSENGERS_SLICE`). _Revenue by tax and fee_ sums the paid trips' `manifest_charges` lines by code, under the name of the latest bill.
  - The **breakdown card** groups revenue by route, origin state, destination state, cargo type, vehicle type, trip type, trip kind or transport company (`DashboardView.breakdown`, computed by the API) and sorts it by revenue, trips or name in the portal (`breakdownRows.ts`: top 9 plus "Others").
- **Search** (`services/govtTrips.ts`, `GovtSearchBar` / `GovtSearch`): one box above the government sections (`govt.search`) finds trips of every company by E-Sali bill ID (or its first 6+ digits), `MNF-…` / `PSG-…` / `MSR-…` number (whole or partial), trip number (`#123`, any length; a bare number of up to 5 digits is a trip number or part of a plate), a passenger's **exact national ID or passport number** (one lookup in `trip_passengers_id_number_idx`), plate in either script and with Western or Arabic digits (`plateSearchKey`; a digits-only query also matches plates), registration, company, driver, sender, receiver or city name, plus an optional origin / destination. Newest first, **paged by the API** (`GET /govt/search`, `ui/Pagination.tsx`; a new search starts on page 1). Every condition is on the trip's own columns, so indexes serve it: the small tables (vehicles, companies, cities) are looked up first and their ids passed as values (`= ANY($ids::int[])`, a condition with no ids is left out: as a subquery that found nothing it still walked every trip), passengers' IDs, payments and certificates are matched as `column = ANY(ARRAY(subquery))`, names through trigram indexes (`pg_trgm`), prefixes through `text_pattern_ops` indexes. What the text can mean is a list of conditions, each searched on its own (its newest 1,001 trips) and merged with `UNION`, never one `OR`: Postgres can't estimate an `OR` of them and walked every trip newest first (2–3 s for a plate with a few trips). The count stops past **1,000** (`SEARCH_CAP`): the page says `more`, the portal shows "1,000+" and the pages stop there.
- **Read-only trip view**: a search result, a dashboard bill or a report opens `TripDetails` with `readOnly` (`GET /govt/trips/:id`: `getTripDetails(null, …)`, any company). It shows the company, the branch and who booked it (name and phone), hides every company action, shows the review panel (_Government review_), and previews attachments (the same `DocumentPreview`, from `GET /govt/documents/:id/file`) and the receipt and manifest. The dashboard and the results stay mounted (hidden) behind it, so going back keeps their state.
- **Exports** (_Export_ on the dashboard, `ExportDialog.tsx`), prefilled with the dashboard's filters. Exports are always in Arabic.
  - **Report (PDF)** (`ReportModal.tsx`): A4 sheets with the letterhead (`DocumentSheet` without barcode or QR). Page 1 has the parameters, key figures, revenue chart (fixed size, Arabic) and trip progress; page 2 has revenue by cargo and by tax and fee, and the breakdown. The user picks the chart grouping, breakdown and sort, and which sections to include. _Print or save as PDF_ opens the browser's print dialog once the chart has drawn, suggesting `masarat-report-<dates>` as the file name (`govt:save-report-pdf` in the demo).
  - **Data (Excel / CSV)** (`services/exports.ts`, `packages/shared/src/exports.ts`): trips (with departure, arrival, kind and ticket price), bills & payments, cargo items, **passengers** and tax & fee lines. Passengers' ID types and numbers are only written with _Include passengers' ID numbers_ (`includeIdNumbers`, off by default: personal data in files that get passed around). The period applies to the trip date, the bill's issue date or the payment date, with a trip status filter. Excel (exceljs) gives one right-to-left sheet per dataset with a frozen bold header; CSV is UTF-8 with a byte order mark, one file per dataset. Excel and CSV can be chosen together. **Exports are built by the export worker** (`src/exportWorker.ts`, its own process: `bun run --filter @masarat/api worker:exports`; one or more, on any machine that reaches Postgres, Redis and the bucket), so a big Excel file never takes CPU, memory or connections from the API instances:
    - **The queue** (`services/exportQueue.ts`, Redis, keys `exports:*`): `POST /govt/exports` checks the options and queues the export (202 with the job); **one per account** at a time (`export_in_progress`). `GET /govt/exports/:id` says how it's going (queued and how many are ahead, being prepared, done, failed with the error and the counts, or cancelled), `GET /govt/exports/current` gives the account's latest (the dialog picks it up again after being closed), `DELETE /govt/exports/:id` cancels it (a queued one leaves the line; one being prepared is thrown away), and `GET /govt/exports/:id/file` streams the file from the bucket with the row counts in `X-Export-Rows`. Only its account sees an export.
    - **How many at once**: across every worker, at most **one per active government admin or supervisor** (`exportConcurrency`; `EXPORT_CONCURRENCY` replaces it); the rest wait, first come first served. A worker claims an export with a 60 s lease that it renews while it works (`services/exportWorker.ts`); a worker that dies loses it, and the next claim marks it failed (`export_failed`).
    - **Building** (`exportData` in `services/exports.ts`): the rows are counted first (an Excel sheet past 1,048,575 rows, `EXCEL_MAX_ROWS`, fails with `export_too_large_for_excel` and the counts, so the user picks CSV or a shorter period), then the trips are read in keyset batches of 5,000 (`exportLimits`) and written as they come to the worker's `<STORAGE_DIR>/exports/<random>` (CSV in one pass, Excel through exceljs's streaming writer, a sheet per pass). Items, passengers and tax lines follow the trips' departure order. Export queries get `EXPORT_STATEMENT_TIMEOUT_MS`. One file goes as is, several as one `masarat-export-<dates>.zip` (fflate, written to disk); the worker uploads it to the bucket (`exports/<id>/<name>`), where it's kept an hour (`EXPORT_FILE_TTL_MS`, then `exports.sweep`), and removes its scratch folder.
    - **The dialog** (`DataExportFields.tsx`) queues the export, follows the account's latest export (polled every 2 s while it's queued or being prepared: "N ahead", "Preparing the files…", _Cancel export_), and saves the file once it's ready; an export finished while the dialog was closed offers _Download_. In the demo, the main process wrote the files straight to a chosen folder.
    - A month of national data (about 590,000 trips and 580,000 bills as Excel) takes the worker about 160 s on 2 cores.
  - The options are checked (`isAnalyticsFilters`, `isExportOptions`) before anything runs. The export dialog has no company filter: exports cover every company. Headers and value labels come from the portal's Arabic translations (`export.columns.*`); plates stay in their stored form, amounts are numbers.
- **Demo data** (`apps/api/src/services/demoData.ts`): only in demo mode (`DEMO_MODE=true`, never in production). On startup, if there are no demo companies (`companies.is_demo`), the 4 demo companies of `DEMO_COMPANIES` (`packages/shared/src/demo.ts`) are created with their roles, 2–3 branches each (in cities on their routes), a company admin, an accountant and a clerk per branch, and about a year of trips, bills (with matching `esali_sim_bills` rows), payments and certificates, using the real trip cost and the taxes and fees as they are when it's seeded. A trip is booked at the company's branch in its origin city if it has one, otherwise at any of its branches, by that branch's clerk. Each trip gets 1–4 cargo items with Arabic names, and about a quarter of tanker trips carry liquids. Some loads are mixed: about 15% of big-truck trips carry a container, and about 10% of fuel tanker trips carry liquids. It is deterministic (fixed PRNG seed, dates relative to today). Each company has an address and TIN, each vehicle a registration number, and 5–8 drivers with Arabic names. Each trip also gets a trip type (imports and exports mostly on Port Sudan routes), sometimes trailers (big trucks), a driver, an Arabic sender and receiver, and packing details per item, and billed trips get the carrier details. All of these come from a second PRNG stream so the trips themselves stay the same. Each company also gets 1–2 **buses** (45–50 seats) with a template for its usual route, and passenger trips on the intercity routes on about 40% of days (mostly full, about 6% with an infant, 5% passport holders), from a third PRNG stream so the cargo trips stay the same; trucks leave between 05:00 and 20:00 and arrive at 50 km/h, buses at 70 km/h. Demo users have `users.is_demo = true`. The Government portal's hidden _⋯ → Regenerate demo data_ deletes the demo companies and everything under them, live and archived (including anything added by hand to one: its trips, members, roles and branches, their sessions, and the trips' reports and decisions), then reseeds; other companies' data and the demo government accounts are kept.
- **Demo accounts** (`DEMO_COMPANIES`, `DEMO_GOVT_ACCOUNTS`; the login page lists `DEMO_ACCOUNTS` in demo mode, and clicking one fills the form). Everyone in a company has the company's password:
  - Government: `ministry.demo` (admin), `ministry.supervisor` (supervisor) and `ministry.agent` (agent), all `govt2026`
  - Company admins: `nile.transport` / `nile2026`, `redsea.logistics` / `redsea2026`, `kordofan.haulage` / `kordofan2026`, `gezira.freight` / `gezira2026`
  - Accountants: `<company>.accountant` (`nile.accountant`, …); clerks: `<company>.clerk1` … one per branch (`nile.clerk1` at مكتب بحري, …). The login page lists the admins, `nile.clerk1` and `nile.accountant`.

## Government review

OCR is out (whether an OCR or document AI service is integrated is still under debate), so government staff review clearances (`packages/shared/src/reviews.ts`, `services/reviews.ts`, routes in `routes/reports.ts` and `POST /govt/trips/:id/cancel`, UI `packages/ui/src/components/trips/ReviewPanel.tsx` and `ReviewDialog.tsx`, Government portal → _Reports_ in `components/govt/ReportsPanel.tsx`). Issuing stays as it is: payment issues the receipt and manifest straight away, and review acts afterwards.

- **Reporting** (`govt.reports.create`: agents, supervisors, the admin): on the read-only trip view of a **certified** trip, _Report_ with a reason (`REPORT_REASONS`: suspected forged document, cargo doesn't match, wrong vehicle or trailers, passengers don't match, other) and a note (1–500 characters, `cleanNote`; `invalid_review` otherwise). Who and when are kept (`trip_reports`). Anything else answers `not_certified`; an archived trip is read-only (`manifest_not_found`).
- **One open report per trip**: a second report is **refused** (`report_open`, 409) while one is open (the trip's row is locked while the report is written, and the partial unique index `trip_reports_one_open_idx` is the backstop). Once that report is dismissed, a new one can be filed.
- **Reports section** (`govt.reports.review`: supervisors and the admin; `GET /govt/reports`): a page at a time, newest first, filtered by status (`open` by default, `revoked`, `dismissed` or all; the filter is kept for the session). A row opens the trip read-only with its attachments, receipt and manifest; the supervisor also opens trips and attachments directly (`govt.reports.review` is enough for `/govt/trips/:id`).
- **Deciding** (`govt.reports.review`): the open report's band on the trip has _Dismiss_ (a note; the clearance stays valid) and _Revoke clearance_ (a reason, the report's by default, and a note). A decided report answers `report_closed`. **Revoking** makes the trip `revoked` (a manifest status), closes the report as `revoked`, and writes the decision to **`trip_decisions`** (action, reason, note, who, when, the report): history is never lost, rows are never deleted (except with the demo companies' trips). The payment and the revenue stay as they were.
- **Cancelling an unpaid trip** (`govt.reports.review`): on a trip pending payment, _Cancel trip_ with a reason and a note. The trip and its payment become `cancelled` (payment status `cancelled`, so it leaves the pending bills), with a `trip_decisions` row (`cancel`); anything but `billed` answers `not_pending`. `cancelTrip` and `refreshBillStatus` both lock the trip, then the payment, so a payment recorded at the same moment either comes first (and the cancel is refused) or finds the trip cancelled.
- **What each side sees** (`TripDetails.decision` and `.reports`, from `reviewOf`): both portals show a revoked or cancelled trip's status and a band with the reason, the supervisor's note and the date; the government also sees who decided and every report with its outcome. **Companies never see reports or their notes**, nor who decided. A revoked trip's bill panel says the clearance was revoked, and the **API withholds its receipt and manifest from the company** (`certificate: null` in `getTripDetails` for a company scope; the government still gets them). The company's trips list filters by both statuses. There is no appeal.
- **The archive**: both tables point to the trip by id **without a foreign key**, so the trip can move. The archive job leaves a trip with an open report live until it's decided, and moves `revoked` trips like any finished one; the status lives on the manifest, so the verify page and both trip pages still show the revocation from the `all_*` views. A revoke whose trip was archived anyway (a report racing the job) revokes it in the archive. Demo regeneration deletes the demo trips' reports and decisions.
- **Planned**: with the SMS integration, a revocation notifies the driver and the company; issuing may later wait for a review.

## Tech stack

**BHVR**: Bun (runtime and package manager), Hono, Vite, React 19. TypeScript everywhere, Tailwind v4, Recharts, i18next.

- **Use bun only, never npm or npx**: `bun install`, `bun run <script>`, `bunx <bin>`, `bun add` inside the workspace.
- Bun blocks dependency install scripts unless the package is in `trustedDependencies`.
- The database is **Postgres + Drizzle ORM** through **postgres.js** (`apps/api/src/db`, config in `apps/api/drizzle.config.ts`, migrations in `apps/api/drizzle`). Locally it runs from `compose.yaml` (Postgres 18 on port **5433**, so it doesn't clash with another Postgres on 5432) with `bun run db:up`.
  - **Two roles** (migration 0010): the API connects as **`masarat_app`** (`DATABASE_URL`: SELECT / INSERT / UPDATE / DELETE, no DDL; checked at startup by `services/dbRole.ts`, fatal in production). Migrations, seeding and the tests' setup connect as the **owner** (`MIGRATION_DATABASE_URL`, `openUnlimitedDb()`). `bun run db:migrate` gives `masarat_app` its development password; in production the DBA sets it. New tables get the grants through default privileges. Company and branch scoping stays in the API (`tripScopeCondition`).
  - **The rolling window and the archive** (`services/archive.ts`, migrations 0011 and 0012):
    - The live trip tables keep about a month (`HOT_DAYS`, 30). The nightly `trips.archive` job moves finished trips older than that (certified, revoked or cancelled, or drafts untouched for `HOT_DAYS`; billed-but-unpaid ones and trips with an open report stay) into the **`archive` schema**, with their items, trailers, passengers, documents, charges, payment and certificate, 5,000 per transaction. `bun run --filter @masarat/api trips:archive` runs it now.
    - `schema.ts` defines the trip tables once (`defineTripTables`) for the live tables, `archive.*` (same columns and indexes, plain ids) and the **`all_*` views** (live UNION ALL archive, `tripViews`).
    - **Reads that may reach older trips go through the views**: the trips list, a trip's page (`archived: true`, read-only in the portals), the government search, exports, the dashboard's live figures, the verify page, vehicles' and drivers' trip counts and in-use checks, the revenue summary's rebuild. **Writes only touch the live tables**; an archived trip answers `manifest_not_found` to edits and billing.
    - A migration that changes a trip table's columns must change both tables and recreate its view (columns listed by name).
    - Selecting a whole view as a nested object (`select({ doc: view })`) comes back empty in Drizzle: name the columns.
  - **Request validation** (`packages/shared/src/schemas.ts`, `apps/api/src/http/validate.ts`): every route's body and query has a zod schema, applied with `body(schema)` / `query(schema)` / `form(schema)` and read with `c.req.valid(...)`.
    - Bad shapes answer 400 `invalid_request` (sign-up and company details `missing_fields`, roles `invalid_role`, the dashboard and exports `missing_fields`) before any service runs, and unknown fields are dropped.
    - Query strings are lenient: unusable values fall back to defaults.
    - Domain rules stay in the services.
    - `doc(tag, summary)` describes each route; development serves the OpenAPI document at `/openapi.json` (hono-openapi).
  - **Time limits**: Postgres stops an API query after `STATEMENT_TIMEOUT_MS` (15 s; it answers `query_timeout`, 503), Bun closes a silent request after `REQUEST_TIMEOUT_S` (30 s, `idleTimeout` in `index.ts`; exports and demo regeneration lift it with `liftRequestTimeout`). Migrations, the test setup and seeding run on `openUnlimitedDb()` or `SET LOCAL statement_timeout = 0`. New long-running work must do the same.
  - **Indexes on big tables**: migrations run in one transaction, so `CREATE INDEX CONCURRENTLY` isn't possible through `db:migrate`, and a plain `CREATE INDEX` blocks writes to its table while it builds. On a database with real volume, run such migrations in a **maintenance window** (`0006` fills `manifests.company_id` and builds about twenty indexes; on a year of national data that takes many minutes). An index can be built beforehand with `CONCURRENTLY` only if its columns already exist and its migration is written to reuse it: `0007` keeps a prebuilt index only when it is valid (`pg_index.indisvalid`) and its definition matches exactly, and builds it otherwise, so a fresh database still works. `0006`'s indexes on `company_id` can't be prebuilt (the column comes with that migration), and its other `CREATE INDEX` statements would fail on a prebuilt index of the same name.
  - Every query is async. One row is `const [row] = await …limit(1)`. A check-then-write that must not race runs in `db.transaction(async (tx) => …)` and locks the row with `.for('update')` (see `lockedStatus` in `services/trips.ts`).
  - Text enums are `text` columns with a CHECK each (`inList`), not Postgres enums, so adding a value is a plain migration.
  - Migrations are a deploy step (`bun run db:migrate`, as the owner), never run by the API at startup. `0000_init.sql` is generated; `0001_reference_data.sql` is a custom migration (`drizzle-kit generate --custom`) seeding Sudan's 18 states (English and Arabic names, without "ولاية", and each one's capital) and 65 cities, the cargo rates, the default taxes and fees, and the government's admin and agent roles. `0002_charges.sql` creates `charges`, `charge_changes`, `manifest_charges` and `pricing_rates` and copies the old tax tables into them (bills keep their lines, now with names); `0003` drops the old tables. `0004_passenger_trips.sql` adds buses, passengers, templates, settings and `departure_at` / `arrival_at` (filled from the trip date, arriving at 50 km/h), and gives clerks `templates.use`; `0005` drops `trip_date`. `0006_scale.sql` (from the load test) enables `pg_trgm`, adds `manifests.company_id` (filled from the vehicles), the indexes the dashboard, lists, search and exports need, and `daily_revenue` (filled from the paid bills); `0007` indexes trips by origin and destination city with the departure. `0008_people.sql` adds `masarat_name_key`, the `people` registry (filled from the passengers' IDs) and `trip_passengers.person_id`, and indexes the dashboard's counts; `0009` drops the passengers' own ID columns. `0010_app_role.sql` creates `masarat_app` and its grants and makes the government admin unique (keeping one admin if a database had several); `0011` creates the `archive` schema's trip tables (generated); `0012` the `all_*` views and the archive's grants; `0013` the dashboard's `dashboard_facts`. `0014_supervisor_role.sql` (generated) widens the role key and permission CHECKs for the supervisor and `govt.reports.*`; `0015_seed_supervisor_role.sql` (custom) seeds the supervisor role (locked, so no `role_permissions` rows); `0016_trip_reviews.sql` (generated) creates `trip_reports` and `trip_decisions` (their grants come from 0010's default privileges) and widens the manifest status CHECK (`revoked`) and the payment status CHECKs (`cancelled`) on the live and archive tables and `esali_sim_bills`. The widened checks are added `NOT VALID`: existing rows already pass them, so the migration doesn't read the trip tables and needs no maintenance window. `0018_dashboard_facts_month.sql` (generated) adds the dashboard's monthly facts. `0017_name_keys.sql` (generated, plus the views by hand) adds the names' stored search keys to the live and archive tables and their `all_*` views; adding a stored generated column rewrites its table (42 s on a month of load data), so on a big database it needs a maintenance window. The archiver leaves generated columns out of its copy (Postgres computes them). A table or column replaced in one migration would make `drizzle-kit generate` ask whether it was renamed: add the new one and copy in one migration (editing a generated NOT NULL column into add, fill, then set NOT NULL), drop the old one in the next. Cities point to their state (`cities.state_id`); the portals show a state's name from the reference data (`format.state`), not from the translations.
  - Always read a generated migration before committing it. Renaming a column makes `drizzle-kit generate` ask an interactive question, which can't be answered here: write that migration by hand (`--custom` with `ALTER TABLE … RENAME COLUMN`) and update the schema to match.
  - Tests (`bun run test`) use their own `masarat_test` database, created and migrated as the owner by `apps/api/test/setup.ts`, then run as `masarat_app` (resetting with `TRUNCATE` uses an owner connection), with the `masarat-test` bucket and their own Redis database (`TEST_REDIS_URL`, default index 2, emptied first). Every test request comes from the same unknown IP, so the tests raise the verify page's limit (`VERIFY_RATE_LIMIT`, 60 a minute by default); the rate-limit tests set it back to 60 themselves. Exports run their worker in the test process: `exportThrough` (`test/helpers.ts`) queues one, drains the queue (`drainExports`) and downloads the file.
  - **End-to-end tests** (`e2e/`, `docs/testing/e2e-scenarios.md`): `bun run e2e` starts its own stack (API on 3200 with its export worker, the web apps on 5275 / 5273 / 5274, a fresh `masarat_e2e` database with the demo data each run) and runs the Playwright scenarios in Chromium. Each spec title carries its scenario id. The specs run under Node, not Bun. Playwright 1.56's browsers on Ubuntu 26.04 install with `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64 bunx playwright install chromium`, and `playwright install` deletes other versions' browsers.
  - **Sudan time**: `config.ts` sets `TZ` (default `Africa/Khartoum`) and the Postgres session uses the same zone. Departures and arrivals are local times and months group in local time, as on the desktop, whatever the host's zone.
  - The migrations were **rebased on 2026-11-22** (companies and roles; there was no real data): a database from before needs dropping and migrating again.
  - When the shape of trip data changes, the migration deletes the **demo companies and everything under them** (their trips, bills, payments, certificates, `esali_sim_bills`, reports and decisions, vehicles, drivers, members, roles and branches), so the next startup reseeds them in the new shape. **Other companies' data is always migrated, never deleted**: new columns start empty, bills already issued keep their lines and amounts, and copies in table rebuilds must keep every existing row.
- Prettier skips `**/drizzle`, so it never reformats the migration snapshots.
- The web apps reach data only through `@masarat/api-client`, never the database.
- **The portals cache what they read** (TanStack Query, `packages/ui/src/lib/query.ts`, `lib/queries.ts`).
  - **Freshness**: data stays fresh for 1 minute; after that, cached data shows at once and refreshes in the background (and on window focus).
  - **Keys**: each list or view has a key (`queryKeys`). Shared lists (vehicles, drivers, branches, reference data, templates, roles, members) are one cached query each, whoever reads them. `useServerList` caches each page (`keepPreviousData`), and so does the government search.
  - **Invalidation**: a change invalidates what it affects. `tripChanged()` covers the trips lists, the trip and the fleet's counts; the vehicles, drivers, branches, roles, templates and members lists are invalidated after their own saves; charges and settings are set from the reply; regenerating demo data invalidates everything.
  - **Errors**: `{ok:false}` becomes `ApiError(code)` (not retried); a network error is retried once. Read the code with `errorCode(query.error)`.
  - **Leaving**: the cache is cleared on logout and when the session ends.
  - **Per-section state**: the government dashboard's filters and view are kept for the session (`lib/useSessionState.ts`). The trips list asks for the current month without dates, so it shares the first page's cache entry.
- **Error boundary** (`packages/ui/src/components/ErrorBoundary.tsx`): each portal section (keyed by section) and the shell show "Something went wrong" with _Try again_ / _Reload_ instead of a blank page.

## Commands

All from the repo root:

- `bun install`
- `bun run db:up` / `db:down` (local Postgres on 5433, Redis on 6380, MinIO on 9000 with its console on 9001, and the buckets; `compose.yaml`), `bun run db:migrate`, `bun run db:generate` (new migration from `schema.ts`)
- `bun run dev`: the API, the export worker and the three web apps together. Or one at a time: `bun run dev:api` (port 3000), `dev:site` (5175), `dev:owner` (5173), `dev:govt` (5174). Open http://localhost:5175 to log in.
- `bun run --filter @masarat/api worker:exports`: the export worker (its own process in production; `bun run dev` starts it)
- `bun run --filter @masarat/api user:create-admin <username> <phone> "<full name>"`: a government admin, for a new deployment
- `bun run dev:demo`: the Electron demo. Run `bun install` in `apps/desktop-demo` first, since it isn't a workspace.
- `bun run typecheck`, `bun run test` (API), `bun run e2e` (end to end, its own stack), `bun run build` (the three web apps), `bun run lint`, `bun run format`
- `bun run --filter @masarat/api trips:archive` (move due trips to the archive now), `storage:migrate` (attachments from the old disk layout to the bucket, once)
- **Load test** (`loadtest/`, see its README): `loadtest/stack.sh` runs a separate Postgres (port 5434), the API (port 3100) and the export worker, each pinned to set CPUs, `bun run --filter @masarat/api load:seed` fills it with national-scale data (only a database named `*load*`), and `loadtest/run.sh` runs the k6 scenarios at a server size and load. `DB_POOL_MAX` sets the API's Postgres pool (default 10).
